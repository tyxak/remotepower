# RemotePower v6.4.2 — "Ver1tyMatters"

Two things about containers that were quietly unfinished, and then a long
correctness pass over the rest of the product.

You can now **silence one container** without silencing its host — the restart
loop you already know about, the sidecar that exits by design, the stack you are
mid-rebuild on. The **Logs** button, which used to queue a command and show you
a toast, now opens a real log window that waits for the agent, tells you it is
waiting, and then lets you actually work with what came back. And the Windows
agent can finally run the container actions the interface has been offering on
its behalf since v6.2.0.

Alongside them, **Thermal** grew the history it never had: temperatures are
folded into long-range roll-ups, so a host's chart now reaches back two years
instead of one day — and any chart that opts in can be zoomed to an exact time
window by dragging it or by typing the times.

The rest of the release is correctness, and most of it has the same shape:
something that looked wired up and did nothing. A schedule that could never
fire. An alert that merged into another host's row and then resolved with it. An
export that ignored the scope its on-screen twin respects. Several of these
fixes correct behaviour the product itself *described* — in a Settings hint, in
a retention promise, in a documentation page that shipped a reference
implementation. Those are called out where they occur, because a promise the
code does not keep is worse than no promise at all.

Four of them were serious enough to be features in their own right. The nightly
**disaster-recovery archive contained none of your fleet** on the installer's
default database. **Restart server** and **Run update now** could not work on a
stock install, and the error they returned sent you to fix the wrong thing. An
**alert aged from its most recent firing** rather than its first, so the
fastest-degrading host was the one that could never escalate. And **nothing
recorded a privileged account being created on RemotePower itself** — while the
same product pages you when someone joins `wheel` on a monitored box.

Filling the gaps those exposed brought new surface with them: **Needs
Attention** and **Tags & groups** are real pages, the alert inbox pages and
filters server-side, shared notification destinations can be scoped to a site
or a tenant, an integration can name the host it runs on, live sessions are
listable fleet-wide, and the metrics endpoint exports eight families of posture
the product has always computed for its own screens and never let you take
away.

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v6.4.2`).

## Mute everything about one container

A host running twenty containers had exactly one alerting granularity: the whole
host. If `decluttarr` restarts twenty-five times a day by design, your options
were to mute `container_restarting` for that host — losing the signal for the
other nineteen containers — or to live with the noise. There was a fleet-wide
`container_alert_excludes` substring list in the config, but it is fleet-wide
and not reachable from the interface.

Every container in **Fleet → Containers → View** now has a **Mute** button. It
silences *every* alert that names that container on that host — stopped,
disappeared, restart loop, and the matching recovery events — while its
neighbours on the same host keep alerting exactly as before.

What a mute does and does not do is worth being precise about, because a mute
you misunderstand is a monitoring gap you do not know you have:

| | muted container |
|---|---|
| Alerts inbox | no new rows; open ones are resolved when you mute |
| Webhooks / e-mail / browser push | silent |
| Needs attention + health score | the container stops counting |
| Fleet event history | **still recorded** |
| SIEM forwarding | **still forwarded** |
| Containers page counts | **still counted**, with an `N muted` note |

The last three are deliberate. A mute is a decision about *paging*, not about
*recording* — Monitoring → Tuning still shows you what you are silencing and how
often it fires, which is exactly the information you need to decide whether the
mute should become a fix. And the Containers page is an inventory: it shows you
everything and flags what is suppressed, rather than hiding it.

Mutes live in the same store as the existing per-alert mutes, so they appear in
the **Monitoring → Tuning** mute list alongside them, labelled with the
container name, and lift from either place. Muting is undoable from the topbar
arrow or <kbd>Ctrl-Z</kbd> like every other low-risk action.

## A container log window that tells you what is happening

Pressing **Logs** used to POST a queued command and toast *"Logs queued — runs
on next heartbeat (~60s)"*. Nothing then showed you the logs. The output landed
in the device's command history, which is not where anyone looks for container
logs.

Now Logs opens a dedicated window that:

- **waits for the agent** rather than returning immediately, and shows a
  progress bar with a live elapsed count while it does — so "still going" and
  "broken" stop looking the same;
- falls back to watching the device's command output if the agent has not
  checked in within the wait window, and says so, in seconds, until it gives up
  after five minutes with an explanation rather than an empty box;
- lets you ask for **100 to 2000 lines** instead of the fixed 50;
- **filters** lines as you type, colours errors and warnings, and keeps the
  whole log for **Copy**, **Download** and the AI **Explain logs** button, so
  filtering the view never silently narrows what those act on;
- can **auto-refresh** every 30 seconds while the window is open;
- keeps the **newest** lines when the agent's 32 KB per-command output cap
  bites, with a marker line saying older ones were dropped — a tail that
  silently returned the *oldest* 32 KB would look complete and be useless.

The same window opens from the device drawer's container table, so there is one
container-log view in the product rather than two.

Two correctness details behind it. The wait is matched to the **exact command**
that was queued, so a logs request sitting behind a queued restart can never
render the restart's output as your container's logs — and a container whose
name is a prefix of another's (`web` and `web2`) can never show the wrong one.
And if the host runs an agent older than 6.4.2, which cannot parse a tail size,
the server drops the request rather than failing the whole command, and the
window says the agent is showing its own default instead of claiming it fetched
what you asked for.

## Temperatures you can look back through

The Thermal page's history column was headed **Trend (~24h)** because that was
honestly all there was. Hottest-sensor readings went into a fixed-size ring
about a day deep, and everything older fell off the end — so "was this host
running this hot last month, before we moved the rack?" had no answer anywhere
in the product.

Those readings are now folded once an hour into the same three tiers the metric
roll-ups already use: 5-minute points kept **8 days**, hourly kept **30 days**,
daily kept about **two years**. Expand a host on **Hardware → Thermal** and above
the per-sensor table you get the whole span as a chart, with **Min / Avg / Max**
per point rather than an average that hides the peaks — four buttons pick 24
hours, 8 days, 30 days or 2 years.

The row's sparkline is untouched and still reads the live ring, which matters on
a new install: the sparkline appears within minutes, and the timeline waits for
its first fold and *says so* instead of rendering an empty box. When a host has
less history than the range you picked, the caption tells you where the history
actually starts, so a three-month line under a "2 years" button never pretends
to be the whole story.

## Pinpointing a window on a chart

The shared time-series helper gained an opt-in **zoom**: drag across the plot to
select a window, double-click to reset, or type an exact **From** / **To** and
press Enter. The fields and both buttons are keyboard-reachable, so this is not
a pointer-only feature. The y-axis rescales to the window, which is the whole
point — a 3 °C excursion is invisible against a full-range axis and obvious
against a zoomed one — and a pinned window survives a data refresh instead of
snapping you back out mid-investigation.

It is turned on in two places for now: the temperature timeline above, and the
**Trends → Device resources** chart, where narrowing to a short recent window
re-fetches the finest roll-up tier that still covers it rather than stretching
the points already on screen. Charts that do not ask for it are unchanged.

## One chart, many hosts

Everything else on **Monitoring → Trends** answers a question about one host.
The **Metric explorer** card answers the cross-host ones: overlay any hosts
against any metrics — CPU, memory, swap, disk, temperature, as average, minimum
or maximum — on a single axis, over any window from 24 hours to two years,
reading the same roll-up history the charts above it read.

Two things it does that a chart usually does not. The roll-up tier is chosen
from the window you asked for and then **said out loud** under the chart,
together with how far back each host's history actually goes — a coarse tier
that has averaged your spike away should admit it rather than present a
convincing flat line. And the eight-hosts-per-run fetch cap is reported in that
same note instead of quietly truncating your selection.

Export CSV gives exactly the series on screen: same hosts, same metrics, same
window, same tier. Saved queries are `localStorage` and the card says so — they
are a convenience for repeat investigations, not something you can send to a
colleague. For that, use a report or a saved fleet query.

## Forecasting that is not only about disks

The Forecast page has always answered one question well — *when does this mount
fill?* — while the daily samples behind it also carried memory, swap and load
average. Months of them, collected and never fitted.

They are now. A **Resource headroom** table sits below the mounts: one row per
metric per host, soonest-to-saturate first, with the current reading, the
ceiling it is heading for, the headroom left and the trend per day. The same
rows appear in each host's drawer, and both `GET /api/forecast` and
`GET /api/devices/{id}/forecast` return a `resources` list beside `mounts`.

The interesting part is what it refuses to do. Memory saturates at 90%, swap at
80%, CPU load at 100% of cores — but a metric sitting *below* its floor
(60 / 5 / 50%) gets no date at all. Extrapolating a machine at 12% memory out to
90% yields a number that looks confident and means nothing. The row still
appears, because the current reading and the trend are useful on their own; the
**Saturates in** column just names the gate that declined instead of inventing a
date — `below floor`, `growth stalled`, `fluctuating` (too noisy for the R²
gate, the same operator-tunable floor the disk projection uses), `>6 mo`, or
`at ceiling` for a host already there, which is a live problem rather than a
forecast.

CPU load is normalised to percent-of-cores, so 100% means one runnable process
per core. A load average that arrives without a core count is dropped rather
than projected: 4.0 is idle on a 64-core box and on fire on a 2-core one.

## Windows hosts can finally run container actions

The Windows agent has reported its containers since v6.2.0, which means the
Containers page has been drawing **Start / Stop / Restart / Logs** buttons for
Windows hosts ever since — and every one of them came back `unsupported
command`. The agent had no handler at all.

It has one now: start, stop, restart, pause, unpause and logs run through
`docker` on Windows exactly as they do on Linux, argv-only with the same
container-id validation. **Update** (pull and recreate) is deliberately *not*
implemented there and refuses with a message saying so, rather than
half-working.

## The DR archive now contains your fleet

A disaster-recovery archive is built by walking the data directory. That is the
whole story only on the single-file JSON backend. SQLite re-adds a consistent
database snapshot alongside the walk — but **Postgres**, the installer default
since v6.1.0, keeps nothing on disk at all, so its nightly archives held no
devices, no alerts, no config, no tickets, no tokens and no vault. They were
tar files of a mostly empty directory, produced on schedule, reported as
successful.

Every database backend now exports its logical documents into the archive under
the same filenames the JSON backend uses, so **one archive shape restores onto
any backend**. `pg_dump` is deliberately not used: it would need a client
binary, credentials and a version-matched server on the restore host, which is
three more things to be wrong on the worst day of the year. The backup result
and the Server status page report `stores` — how many documents the archive
carries — so a hollow archive is visible before you need it rather than after.

Restoring one did not work either, on any backend. Scheduled archives prefix
every member with `remotepower/`, and `POST /api/backup/restore` joined member
names onto the data directory verbatim: uploading a nightly archive recreated
the whole install one directory down and restored nothing usable, while
cheerfully reporting how many files it had restored. The restore strips that
root when every member carries it, and then **imports the stores into the
database**, because on SQLite and Postgres the extracted files are inert — reads
go to the database, not the disk. The response reports `stores_imported`.

The weekly restore drill passed throughout, because all it asserted was that
the tar opened and had a `remotepower/` member — which a hollow archive
satisfies perfectly. It counts the restorable state an archive actually holds
now and fails when there is none, and it persists what it found, so Server
status shows what is in the archive rather than only whether the drill passed.

## Restart and update work under the hardening we ship

**Restart server** and **Run update now** could not work on a stock install.
The shipped `remotepower-wsgi.service` sets `NoNewPrivileges=true`, which blocks
sudo's setuid transition regardless of any sudoers drop-in — the same fact the
WireGuard helper documents as its reason for running sudo-free on ambient
capabilities. Both helper scripts re-exec themselves under `sudo -n`, so
neither could ever escalate. Worse, `restart_available` was a bare
file-exists check, so the button was offered, always failed, and the error
pointed the operator at a sudoers rule that could not have fixed it.

There is a real preflight now, and a route that works *with* the hardening
rather than asking you to remove it. Four systemd units —
`remotepower-server-restart.path` + `-run.service`, and the matching `update`
pair — watch the data directory for a request file and perform the action as
root. The app server creates an **empty** file in its own `ReadWritePaths=`
directory, so the only thing it can express is which of two fixed actions to
run: never a command, never an argument. Where sudo does work (an unhardened
unit, or running as root) that path is unchanged; where nothing can work, the
error says so and names both ways out. Request files are excluded from
archives, so a restore can never queue an action on the host it lands on.

Installing the units is two commands and is covered in
[upgrading.md](upgrading.md).

## Alerts age from when they broke

An alert carried only `ts`, and `_record_alert` rewrites `ts` to the newest
occurrence every time it coalesces a repeat firing. So everything that measured
elapsed time on an open alert was measuring the wrong thing.

The sharp edge was escalation. An edge-triggered condition that re-fires faster
than its first escalation tier — `nic_errors` fires on every ~60s heartbeat,
tier one defaults to fifteen minutes — reset its own age on every fire and could
therefore **never escalate**. The fastest-degrading host in the fleet was the
one nobody got paged about. MTTA and MTTR had the same flaw from the other end:
an alert acknowledged four hours after it broke reported zero.

Alerts now carry **`first_seen`**, preserved through coalescing and falling back
to `ts` for rows written before this change, and `_alert_first_seen()` is the
single accessor every elapsed-time consumer goes through — escalation tiers
included. The inbox shows age from the first occurrence rather than from the
most recent re-fire, which is the number you actually want when you are
deciding what to look at first.

## An inbox with more than one page

The alert inbox always asked for 500 rows and had no way to ask for the next
ones. Past 500 the rest were simply unreachable, and the client-side filter box
searched only the loaded slice — so an operator looking for the host their
pager had just fired on got *"no alerts in this view"* and reasonably concluded
it had resolved itself.

`GET /api/alerts` now takes `offset` alongside `limit`, plus:

| Parameter | Effect |
|---|---|
| `q` | case-insensitive substring over device name, event and title |
| `severity` | `critical` / `high` / `medium` / `low`; repeatable, or comma-separated |
| `device_id` | exact match |

and returns `total`, `offset` and `limit` in the envelope. Everything new is
optional and the envelope is a superset of the old one, so existing callers are
unaffected. `total` is computed **after** the scope and tenant visibility
filter, so it can never count a row the caller is not allowed to see.

## RemotePower watches its own privileges

Nothing in the product fired when a privileged account or a security control on
**RemotePower itself** changed — while the same product pages you when someone
joins `wheel` on a monitored box.

Creating an admin, promoting a viewer to admin, minting an admin-role API key,
emptying MFA enforcement, disabling change approval and clearing the audit log
now raise **`control_plane_security_change`** through the normal event path:
alerts inbox, webhooks, e-mail, browser push and the activity feed, with the
payload keys added to both whitelists (the half that silently drops fields when
it is missed). It routes on the `accounts` kind, so an operator who already
sends privileged-account events to a security destination gets these on the
same wire. It is a *point* event with no recovery, deliberately — an
auto-resolving row would let a real escalation disappear from the inbox the
moment the attacker undid the visible half of it. `handle_user_create` had no
audit entry at all before this.

Two related gaps closed with it:

- **A device joining the fleet was never recorded.** The enrollment handler
  built an audit entry for re-enrollment and for both denial paths and left the
  successful first enrollment as `None`, with no event to match — so the audit
  log could show when a host re-enrolled or was decommissioned, but never when
  it first appeared. **`device_enrolled`** records it now, and is explicitly
  kept out of Needs Attention: a new host is news, not a problem.
- **No user record carried a last-login time**, so there was no dormant-account
  signal and no access review, and an admin could revoke sessions without ever
  being able to see them. Users carry **`last_login`** now, and **`GET
  /api/sessions`** lists every live session fleet-wide — who, which role, from
  where, since when. Admin-gated, audited, and scoped to the session owner's
  tenant. Session tokens only (API keys are a separate credential with their own
  list), and the raw token is never returned — `id` is the same one-way handle
  the per-user revoke endpoint takes.

## Notifications that reach the right people

**An integration instance had no host.** That sounds like a schema detail and
was not. `integration_down` carried no `device_id`, was absent from
`SUPPRESSIBLE_EVENTS`, and `_alert_muted` bails on any payload without a device
— so rebooting a NAS inside a maintenance window you had declared correctly
suppressed the host going offline and then paged you once per self-hosted app
it runs, at 3am, with no way to silence it short of disabling each integration
by hand.

An instance can now name a **device** and a **site**. Both are optional, so an
unbound instance behaves exactly as before. Bound, its up and down events carry
a device, which is what makes maintenance windows, per-(host, event) mutes,
unmonitored-host suppression and scoped routing apply to them like any other
device event. The binding opened one new hole and closed it in the same pass: an
instance bound *after* its down-alert was recorded left the stored row without a
device while the recovery carried one, which the identity guard would have
stranded open forever.

**Shared notification destinations could not be scoped.** Every destination
received every enabled event from every tenant, and e-mail had a single global
recipient list — so an MSP running three customers had no way to send each
customer's alerts to their own channel, short of creating a fake operator
account per customer to hang a personal webhook off.

Destinations now take the same group / tag / site filter personal subscriptions
have always had, plus a tenant allowlist. E-mail gains **`email_routes`**: any
number of additional recipient lists, each with its own scope, alongside the
global `smtp_recipients` list — which can itself be scoped with
`smtp_scope_filter` and `smtp_tenants`. The filter is applied at the two
delivery chokepoints rather than at each of the ~200 firing sites, so every
event is covered by construction.

Three properties worth knowing:

- **An absent filter still means everything**, which is what every existing
  destination has. Nothing you have configured changes behaviour.
- **A scoped destination does not receive an event it cannot attribute to its
  slice.** "Tenant A's Slack" asked for tenant A's events, and a fleet-wide
  monitor or a server-side sweep is not one. When that leaves no destination at
  all, one `filtered` row is logged, so an event reaching nobody is visible
  rather than silent.
- **The operator-triggered Test event bypasses scoping on purpose.** That
  control exists to prove a destination works, and quietly delivering nothing
  would defeat it.

## Metrics for the posture we already compute

`GET /api/metrics` grew eight families — temperature, SMART, UPS, backup
freshness, disk-fill ETA, risk, reliability and baseline compliance. All of it
is posture the product already computes for its own screens and could not
export, so a Grafana user could not alert on a failing disk or a stale backup
from RemotePower's own endpoint.

| Family | Series |
|---|---|
| Temperature | `remotepower_device_temperature_celsius`, `…_temperature_max_celsius` |
| SMART | `remotepower_device_smart_disk_healthy`, `…_smart_disks_failed`, `…_smart_wear_ratio`, `…_smart_spare_ratio`, `…_smart_pending_sectors`, `…_smart_reallocated_sectors`, `…_smart_power_on_seconds` |
| UPS | `remotepower_ups_on_battery`, `…_ups_runtime_seconds`, `…_ups_battery_charge_ratio`, `…_ups_load_ratio`, `…_ups_input_volts`, `…_ups_power_watts` |
| Backup freshness | `remotepower_backup_ok`, `…_backup_age_seconds`, `…_backup_max_age_seconds` |
| Disk-fill ETA | `remotepower_device_disk_fill_eta_seconds` |
| Risk | `remotepower_device_risk_score`, `remotepower_risk_devices` |
| Reliability | `remotepower_device_reliability_score`, `remotepower_reliability_devices` |
| Baseline compliance | `remotepower_device_compliance_pass_ratio`, `remotepower_compliance_pass_ratio`, `…_compliance_check_devices`, `…_compliance_devices_evaluated` |

Each block is gated on a context key, and the context builder supplied none of
them — so every family was unreachable on a live scrape while every test passed.
That is the "feature that can never fire" shape this codebase keeps hitting,
caught here before release rather than by a user. They are wired now, and
measured at 14ms cold and 5ms warm on a 300-host fleet, because the two
O(fleet) scores go through their existing caches.

One naming trap worth stating: the backup family reads the **per-device
backup-monitor** store, not the control plane's own DR state. The two share a
name prefix and nothing else.

## Two pages that were missing

**Needs Attention has a page.** The digest had exactly one consumer — a
dashboard card showing the first ten items with no total, no filter and no way
through to the rest — while fleet health is derived from the very items the
operator could not enumerate. The page is that digest in full: sortable,
filterable by severity, kind, host and free text, with per-severity counts and
the same snooze and ignore actions the card offers. It is recomputed from
current fleet state on every load and never read from a stored queue, so an item
disappears the moment its cause clears. See [attention.md](attention.md).

**Tags and groups have a page too.** They drive role scopes, alert routing,
service baselines, auto-patch scopes, rollout rings and report scopes, and there
was no way to even list them with counts — let alone rename one across the
fleet. Both are listed now with device counts, ungrouped and untagged totals,
and click-through to the matching devices. **Rename**, **merge** and **delete**
ship for tags, and a rename onto a name already in use *is* a merge, which the
confirmation says before doing it.

Groups stay read-only for now, deliberately: the only server-side primitive is
one device at a time, and a loop that half-applies leaves a group half-renamed,
which is worse than not offering the button. Counts derive from the device list
the operator can already see, so they inherit its scope and tenant filtering for
free — a tag used only on out-of-scope devices correctly never appears.

## WordPress monitoring that reports the site, not the connector

Field reports of the WordPress connector answering `invalid JSON` for sites that
were perfectly healthy. The site was fine in every case. The connector was not.

- **The REST index was too big to read, and the site got the blame.** The
  connector fetched the unfiltered index, which enumerates every registered
  route with its full schema — routinely several megabytes on a site running
  WooCommerce, Yoast or Elementor. The transport reads a bounded 2 MB, so the
  body arrived truncated mid-object and the operator was told their JSON was
  invalid. It asks for the four keys it actually reads now, which turns a
  multi-megabyte fetch into a few hundred bytes.
- **Truncation is reported as truncation.** The transport reads one byte past
  its budget so it can tell a complete response from a cut one, and any
  connector that hits the cap now says so. That covers large Kubernetes and
  OpenShift responses too, which had the same silent failure.
- **`invalid JSON` was the answer to every question.** That one string covered
  an HTML login page, a WAF interstitial, an empty body, a truncated read and
  genuinely broken JSON. Each reports its own cause and what to do about it now.
- **A PHP notice no longer breaks monitoring.** A theme or plugin emitting a
  warning prepends it to every REST response; the JSON after it is valid and the
  site is healthy. RemotePower reads past a short prefix (and a byte-order mark)
  rather than turning somebody else's cosmetic warning into "your monitoring is
  broken".
- **Plain permalinks work.** With permalinks set to *Plain* there is no
  `/wp-json/` path at all — the REST root is reachable only through a query
  parameter. That was a permanent, unexplained 404 for those installs; both
  forms are tried now.
- **"Credentials rejected" was blamed for everything.** A 404, an HTML login
  page and a genuinely wrong password all pointed the operator at the
  Application password. They are told apart now — including the common case
  where a CGI or FastCGI host strips the `Authorization` header before PHP ever
  sees it, where the password is perfectly correct and that advice sends you to
  the wrong place. Application-password spaces are stripped, too: WordPress
  displays the password in space-separated groups and ignores the spaces itself,
  so pasting it verbatim was reported as a wrong password.
- **Every login timestamp was zero.** The date was parsed only in MySQL's
  space-separated form, but WordPress core's REST layer serialises ISO 8601 with
  a `T` — so the table showed `—` for every row and the 24-hour login count sat
  permanently at 0, which is indistinguishable from a quiet site. That count
  could also never exceed 5, because the scan stopped as soon as it had five
  rows to display. Both date forms parse now, and the count runs across the
  whole scanned window while the table still shows five.
- **A `null` body was reported healthy** — a green "site up" tile for something
  that was never confirmed to be WordPress at all. A body that was valid JSON
  but not an object crashed the parser outright.
- **The login panel stayed on screen after the homelab feature was switched
  off.** The kill switch replaced the tile grid but never touched the sibling
  panels, so remote usernames and source IPs remained visible for the life of
  the tab.
- The documentation and the in-app card said "the last 5 successful logins"; the
  connector returns the 5 most recent it finds while scanning a bounded window
  of the login channel. Reworded to what it does.

## Alerts you can trust

- **Every certificate expiring on one port was a single alert.** A `tls_expiry`
  target is not a device, so an alert's identity came down to the event and the
  port — and every certificate expiring on :443 coalesced into one inbox row.
  Renewing the first host then auto-resolved that row, and the rest expired with
  nothing in the inbox at all. The host is part of the identity now, so each
  certificate keeps its own row and its own recovery.
- **An escalating alert never changed severity.** A repeat firing refreshed only
  the timestamp and the count, so a disk going from 85% to 96% kept reading
  *medium* in the inbox while the webhook, SIEM and push channels had already
  paged on *critical* — the inbox disagreeing with the page the operator had
  just received. Escalate-only, so a transient dip cannot silently downgrade a
  live page.
- **The alert cap deleted open alerts on SQLite and Postgres.** Resolved-first
  eviction shipped for the JSON backend in v6.4.0; the database backends — the
  enterprise default — kept evicting oldest-overall, so on a fleet past the 5000
  cap the still-open alerts went and the resolved ones stayed. The retention
  hint promises that open alerts are never purged. All four cap sites across
  both backends now keep that promise.
- **Every CRIT log rule was filed as medium.** The log engine fires with
  `severity` and the severity resolver read `level`, so a CRIT rule disagreed
  with its own needs-attention card, was dropped by minimum-priority filters,
  and never reached web push or broke through quiet hours.
- **A CVSS v4.0 advisory scored `unknown`.** NVD and OSV have published v4
  vectors since 2023 and advisories increasingly carry only one; it fell through
  every branch of the score parser, so a 9.8 was filed as neither critical nor
  high — no risk points, no CVE alert, invisible to the SLA and compliance
  views. The v4 base metrics are mapped onto the v3.1 formula now and the source
  is labelled `cvss_v4_approx`, because it is a derivation and not an official
  v4 base score.
- **A certificate that could not be reached was reported as expired.** An
  unknown expiry was encoded as zero days remaining, which is also what "expires
  today" looks like — so a transient DNS or connection failure raised a critical
  certificate-expiry alert. Fixed in the alert path and in needs-attention;
  unreachability is already its own signal.
- **IPv6 brute-force sources were truncated to their first group**, so unrelated
  attackers shared a single counter. That counter crossed the threshold on its
  own and fired an alert naming an address nobody can block, while the real
  per-source signal was diluted away.

## Scheduled work that actually runs

- **Six kinds of scheduled work fired only if the clock happened to land on the
  right minute.** Scheduled commands, backup jobs, auto-patch, both report
  senders and recurring tickets were evaluated with an exact-minute match. Under
  the out-of-band scheduler — the default since v6.1.0 — ticks are a
  fixed-period sequence rather than a per-minute sample, so at any interval
  above 60 seconds the phase relative to a day is constant: a daily job was
  either always sampled or never sampled. At 120, 300 or 600 seconds a daily
  schedule ran on 0 days out of 30. Nothing logged it, and the policy still read
  as enabled. They evaluate the elapsed minutes now, the way a real cron daemon
  does — which is what the scheduler's own documentation already described.
- **Three cron evaluators, with three different sets of capabilities, all of
  which accepted what they could not evaluate** — so a schedule the validator
  allowed simply never ran. A maintenance window of `0 22 * * 1-5` suppressed
  nothing, and with command gating on it held every exec and upgrade for its
  devices forever, waiting for a window that could not open. `dow=7` — Sunday,
  which every crontab accepts — matched nothing at all. A quarterly `*/3` ran in
  March/June/September/December instead of January/April/July/October, because
  the step anchored at 0 rather than at the field's minimum. There is one
  evaluator now, handling lists, ranges, steps, steps on ranges, and Sunday as
  both 0 and 7.
- **Audit-log retention was never enforced.** The daily retention sweep armed
  only if some retention setting was explicitly greater than zero, and audit
  retention is the one key with a non-zero default — so on a stock install the
  90-day retention that Security status and the `audit_retention` compliance
  control both report as effective was never actually applied.
- **"0 = off" now means off.** The UPS critical-runtime trigger and the AI
  per-user daily request cap both read their value in a way that could not
  distinguish an explicit 0 from unset, so switching either off silently
  restored the default.

## Exports and reports

- **Patch-report CSV, patch-report XML and the fleet SBOM ignored role scope and
  tenancy.** All three share a helper that read the whole device store and
  applied only the URL's own filters, so an operator restricted to one group
  could download the entire fleet's patch state or software inventory. The JSON
  version of the very same report has always filtered correctly, which is
  precisely why this stayed invisible: right on screen, wrong in the export.
- **The mute list on Monitoring → Tuning was not scope-filtered.** The
  noisy-events timeline one line above it was. A tenant-scoped administrator
  could read every other tenant's muted alerts and the hostnames attached to
  them. It required a signed-in account and was never reachable without
  authentication.
- **Knowledge search returned hosts the caller cannot see.** The AI chat path
  deliberately withholds retrieval from scoped roles, because the knowledge
  index is not tagged per scope; the standalone search endpoint ran the same
  index for anyone signed in, returning device notes, open ports and inventory
  for out-of-scope hosts. It refuses for scoped and tenant-limited callers now,
  which is the honest answer until the index carries those tags.
- **Spreadsheet formula characters are neutralised in the posture report.** A
  device name is operator-set text, and a spreadsheet treats a cell that begins
  with a formula character as a formula rather than as a name. Every sibling
  exporter already neutralised those cells; the fleet and site posture report —
  the CSV most likely to be mailed to a customer — was the one that did not. It
  does now, and the neutralisation is applied centrally so a future row cannot
  reintroduce the gap.
- **Custom report downloads failed whenever a section was unticked.** The CSV
  renderer required every block to be present, so the exact URL the Download
  button builds returned an error for any saved definition that left one out.
  Its e-mail sibling has tolerated subsets since v3.14.0.
- **An apostrophe in a note destroyed the record.** The helper that escapes
  values into HTML attributes emitted JavaScript-string escapes instead of HTML
  entities, and a browser hands those back literally — so the round trip through
  the attribute produced invalid JSON. A timesheet entry's **Edit** button
  opened a blank form, and **Save** then wrote the blank over a real billing
  record. Rate names, invoice prefixes and the issuer name printed on invoice
  PDFs were corrupted the same way. Every one of the helper's call sites is
  a quoted HTML attribute and none is a JavaScript string, which is what makes
  emitting entities the correct fix rather than a compromise.
- **Hours logged in the evening landed on the wrong day.** Time entries
  defaulted to the UTC date, so evening entries in the Americas and
  after-midnight entries in Europe fell on the wrong day, week and invoice
  month. The timesheet CSV separately labelled the file with one ISO week and
  fetched another.

## Reading the whole file, and the whole rule set

- **nftables rules that open a port were missing from the firewall inventory.**
  The parser told rules from headers by looking for a brace, on the stated
  assumption that only headers contain one. An anonymous set puts braces in a
  *rule* — the standard modern nft idiom, and what firewalld generates. So on
  every firewalld host, exactly the rules that open a port or allow a source
  vanished from the inventory, from the deletable rule list, and from the rule
  count the per-asset risk score derives from. An operator auditing what was
  open on that box saw the established-connection and loopback rules and
  concluded nothing was exposed. Five rules of five are reported now, where two
  of five were before.
- **Append-only logs froze on their oldest content.** The agent's bounded file
  read returns the *first* N bytes, and ClamAV appends a summary block per run —
  so once `scan.log` passed its 40 KB cap the parse was stuck on ancient data
  permanently. That is not just a stale drawer: `av_infected` is edge-triggered
  on the count rising between heartbeats, so a frozen count can never rise and a
  genuine new detection could never fire the critical alert, while a host
  cleaned months ago stayed dirty in the drawer, the attention items and the AI
  corpus. ClamAV, rkhunter and the `auth.log` sudo fallback read the tail now.
- **Log collectors went blind after every rotation.** The web-access and
  apt-history collectors persisted a byte position and seeked to it, so once
  logrotate replaced the file — or truncated it in place — the stale offset
  pointed past the end: nothing was read, the position was rewritten unchanged,
  and every line below it was dropped until the new file grew past the old size,
  which on a quiet host is days. Access-log rules — authentication failures, 5xx
  spikes, scanner probes — simply stopped firing after each nightly rotate, with
  no error anywhere. Both now detect a changed inode or a shrunk file and
  restart, which is what the general file-log collector has always done.
- **Duplicate-MAC detection could never fire.** The check read an interface list
  off the CMDB record, whose row specification has no MAC field at all, so the
  comparison was structurally always empty and the check collapsed to the single
  primary MAC captured once at enrolment. The multi-NIC clone — the "cloned VM
  whose NIC was never regenerated" case the check exists to catch — was
  therefore never detected. It reads the per-NIC addresses the agent already
  reports.
- **Kernel log entries were all dated at ingest.** The agent parses the
  timestamp out of `dmesg` and strips it from the message, so the server had
  nothing left to find and stamped every kernel error with the time it arrived —
  wrong by up to the agent's 24-hour look-back window, and re-dated again after
  each agent restart. The entry's own event time is used as the fallback now.

## Windows and macOS report what Linux reports

- **Every mount on a Windows host was dropped at ingest.** The sanitiser
  required a leading `/`, so the storage view, every per-mount disk check and
  the disk-fill forecast were permanently empty for Windows — which reads as
  healthy.
- **Loopback services were reported as world-exposed on Windows and macOS.**
  Both classifiers tested loopback against an exact three-value list and fell
  through to "world", so `127.0.0.2`, the uncompressed spelling of `::1`, and —
  the common one — the IPv4-mapped address a dual-stack socket reports for an
  IPv4 bind, each raised a high-severity "port exposed to the world" alert for a
  service bound to localhost. The server does not recompute the scope, so the
  alert stood. All three agents share the same address parsing now, and an
  address that cannot be classified still counts as world-exposed: an exposure
  we cannot read should fail loud. The same parsing closed the mirror-image
  defect, present on Linux since v3.11.0, where the mapped spelling of a
  wildcard bind classified as LAN and silenced the check entirely.
- **A macOS host with a custom check assigned lost its record eleven beats in
  twelve.** Check results are reported every beat by design, but the server
  replaced `sysinfo` wholesale — so the one-key dictionary wiped uptime,
  platform, kernel, mounts, listening ports and every percentage between cadence
  beats. That host's Checks page collapsed from 14 rows to 2, so a filling disk
  or an exposed port reported nothing wrong about 92% of the time. A partial
  beat is flagged and merged now, keeping both properties.
- **"Scan disk usage" refuses on Windows instead of pretending.** The `du`
  collector is Linux and macOS only, and the Windows agent has no reader for the
  flag at all — so the heartbeat popped it and threw it away while the operator
  got a green "runs on the next heartbeat" toast and a report that never
  arrived. The server refuses honestly now, and the drawer explains why rather
  than drawing a button that cannot work.

## IPv6 addresses stopped disappearing

- **Every IPv6 address was silently blanked, everywhere.** The shared IP
  sanitiser's pattern matched only the fully expanded eight-group form, so a
  compressed address, `::1` and an IPv4-mapped address all became empty strings
  with nothing logged. It surfaced through the WordPress login table, where a
  row read `admin | — | Denmark (DK)` — an IP-less login with a country, which
  looks like corruption — but the same helper guards the audit log's source IP,
  device create and update, the interface inventory and the gateway, so an IPv6
  network's addresses quietly vanished from all of them. Validation goes through
  Python's `ipaddress` module now, with the old pattern kept as a fallback so
  nothing that was accepted before is rejected.
- **"Send IP addresses = off" did not hide IPv6 addresses.** The AI privacy
  toggle's matcher had the same expanded-form-only limitation, so every address
  anyone actually writes went to the provider verbatim while the toggle read as
  on. A long address could even match in two halves, which *looks* redacted in a
  spot check.

## Settings that stay saved

- **The write lock handed back stale data.** The locked-update helper acquired
  the file lock and then read through a per-request memoiser, so it returned a
  snapshot taken *before* the lock existed and wrote that snapshot back on exit.
  That is the exact guarantee the helper exists to provide, and the one about
  two dozen handlers were moved onto it for. A device enrolled by a concurrent
  process was absent from the stale copy and was deleted by the locked write,
  taking its token with it; the same root cause dropped sessions created during
  a login. Both database backends already read inside their transaction. The
  file backend agrees now.
- **Twenty-three places rewrote the whole configuration document from a stale
  snapshot.** Each read the config, changed one key and saved the lot back with
  no lock held across the pair. It was worst in the periodic sweeps, where a
  configuration save landing mid-run had its keys silently reverted — losing the
  IP-allowlist enable and the SMTP host, which is a security setting turning
  itself back off minutes after an administrator switched it on. Timestamp-only
  claims take a dedicated slot claim now, the rest take the lock, and a
  configuration save applies only the keys the request actually changed.
- **Sixteen per-device stores had the same unlocked read-modify-write on the
  heartbeat path.** Concurrent workers dropped each other's device rows
  outright. Losing a listening-port or authorized-key baseline row is worse than
  losing telemetry, because the host then re-baselines and the new-port and
  new-authorized-key detections never fire again.

## Numbers that say when they cannot be measured

- **The SLO error budget was structurally binary.** A 99.9% target allows 0.1
  percentage points of downtime, but a window bounded by 300 stored checks can
  only express multiples of 0.33pp — so the remaining budget could only ever
  read 100% or 0%, presented as a precise number, and exported to Prometheus as
  a hard breach the instant one check failed for a probe that was up 99.67%.
  Widening the window to a time span does not help, because the window is
  bounded by sample count either way. The information is genuinely absent at
  that resolution, so it is reported as absent: the table says "too few checks"
  and explains the arithmetic, and the Prometheus budget and burn-rate gauges
  are omitted for those monitors rather than published wrong. Widening the
  stored check history or relaxing the target makes it measurable again.
- **Control-plane availability reported 100% through a total app-server
  outage.** The hourly "we served a request" bucket rode the periodic-sweep
  helper, which returns early under the external scheduler — the install default
  since v6.1.0 — so the only writer left was the scheduler daemon, which ticks
  whether or not the app server is up. The bucket's whole contract is that the
  control plane served a request, so only the request path stamps it now.
- **Prometheus per-device health keyed on the display name.** Two hosts sharing
  a name — cloned images, a default `raspberrypi`, a multi-site estate — emitted
  the same series identity twice, so one of them was dropped as a duplicate
  sample and had no health score at all; and even with unique names, no join
  against the online, CPU or CVE series could ever match. It keys on the device
  id like every other per-device family, with the display name carried as a
  separate label.

## Documentation that described behaviour the code did not have

- **Webhook replay protection was promised, not delivered.**
  [webhooks.md](webhooks.md) told receiver authors to bound the timestamp to
  reject replays, and shipped a reference verifier that did so — but the
  signature covered the request body alone, which leaves the timestamp header
  unauthenticated and an age check over it meaningless. A body-only signature
  cannot support replay protection. Rather than delete the promise, deliveries
  now carry a second signature header whose MAC covers the timestamp as well as
  the body (the standard construction), sent **alongside** the legacy header so
  no deployed receiver breaks. The documentation recommends the new header and
  says plainly that the body-only one is not replay-protected.
- **`automations.md`'s only worked example could never fire.** It was built on
  an event name that has never existed — not in the event registry, never fired
  anywhere. Rule validation accepts any string, so the rule saves, shows as
  enabled, and is skipped for every real event; its fire count stays 0, which is
  also what a correct rule looks like on a healthy fleet. The invented name had
  spread further than the page: into two source comments and, worst, into the AI
  system prompt that suggests automations, from which the model would
  confidently teach operators to build the same dead rule. `agent-commands.md`
  had the same defect, naming a backup-verification event that does not exist. A
  guardrail now fails the build if a documentation page that teaches
  rule-building — or the AI prompt's own example list — names an event outside
  the registry.
- **`features.md` claimed volumes are never pruned** while the handler ships
  both the volume and the full prune, and while the row four lines above it
  documented that correctly. The stale row is gone; its one accurate fact — that
  the *scheduled* prune is restricted to the safe scopes and can never select
  volumes — moved into the row that survives.

## Smaller operator-facing fixes

- **A firewall rule carrying a comment or a negation could not be deleted.**
  iptables renders rule specifications with shell quoting, and the character
  allowlist that guards a rule you *type* rejected both forms — so the Delete
  button the Firewall page draws for every listed rule answered an error on
  every Kubernetes node, and on any host whose UFW application profiles put a
  comment in the chain, about a rule the operator never typed. Widening the
  shared allowlist would have loosened the guard on the rule you add, so the
  delete reference is parsed into tokens and each token re-quoted instead: the
  command is safe by construction whatever the rule text holds. The reference
  stays the exact rule spec rather than a position, because the command runs
  minutes after the listing was taken and a positional delete on a busy chain
  would remove something else.
- **The IP allowlist blocked agents it promised not to.** Enabling it broke the
  agent self-update signature fetch — so an agent downloaded an update it then
  refused to install — along with the live-metrics push and the file-manager
  transfer the agent posts when you download a file from a host, while the
  Settings hint said it never blocks an agent.
- **Proxmox snapshots with a hyphen could be seen but not used.** `pre-upgrade`
  is a name Proxmox creates happily; it was listed with working-looking Rollback
  and Delete buttons that always refused it — discovered at the moment a
  rollback matters most.
- **A hostname with an underscore was silently rewritten rather than rejected.**
  `db_primary` was enrolled as `dbprimary`. Underscores are forbidden by RFC
  1123 and ubiquitous in practice, and every later join on the hostname then
  failed against the machine's real name — including the EDR coverage
  cross-reference, which reported a protected host as uncovered. A false
  "unprotected" is what teaches an operator to stop reading that list.
  Underscores are kept now; genuinely unsafe characters are still stripped.
- **Agentless hosts reported a load average of 0.0 for any load below 1.00.**
  The remote probe parsed `uptime` output by splitting on commas, which is also
  the decimal separator in most of Europe. It reads `/proc/loadavg` under a
  pinned C locale now, so the agentless CPU check can actually leave "ok".
- **A board tile did not carry its filter.** Clicking a group, site or tag tile
  opened the full, unfiltered fleet, so the operator had to re-apply by hand the
  very filter the tile exists to apply — worst on a large paginated fleet. The
  tile sets the filter now, including the board's own synthetic "no group" and
  "no site" buckets, and the group dropdown gained the Unassigned option it was
  missing.
- **Copy host summary read four facts the server does not store.** CPU model,
  RAM, load average and temperature were read under key names the heartbeat
  sanitiser does not write, so all four were absent from every summary ever
  copied — and the core count went with them, because it hung off the same dead
  check. It reads the keys the drawer's own Overview pills use; the temperature
  line, which could never have carried data, is gone.
- **Events in the device drawer had no severity colour.** The dot beside each
  event referenced a style class with no rule at all, so it rendered as a
  zero-size element and every event in that tab looked identical, critical and
  informational alike. Three of the most severe event names were separately
  mapped to a severity class that does not exist.
- **The EPSS cache stored the whole feed when there was nothing to enrich.** A
  bound meant to keep only the scores matching current findings short-circuited
  itself when the finding set was empty — which is exactly the state it was
  written for, a server before its first scan — so roughly 290,000 rows were
  kept and rewritten daily.
- **The network-map knowledge source indexed the wrong store.** Topology edges
  live on the device record; the source watched the shared bookmark dashboard,
  so declaring or clearing an edge never invalidated the index and half its
  corpus was always empty. The self-observability corpus separately read an
  error field no producer writes, so a hard-failing sweep was indexed as "— ok".
- **The device drawer's container Logs button** passed the container name
  through a dispatcher that coerces anything numeric-looking to a number, so a
  container called `0x10` was requested as `16`. It passes the raw name now.

## The security finalize pass

An adversarial audit of the whole release — every finding required to carry a
runnable reproduction — and a fresh hunt across older code found and fixed:

- **A cross-tenant log-content leak.** The live-tail log endpoint returned every
  device's collected log lines with no scope filter, while its search sibling had
  been scope-filtered since v6.2.2. A read-only role or a tenant administrator
  could tail other scopes'/tenants' log content, or name an out-of-scope device
  and read its lines. The tail endpoint now filters the device set exactly as
  search does.
- **A governance switch a config import could flip.** Change-approval (four
  eyes), the MFA-required roles and the audit-retention floor are step-up-gated
  on the Settings save path; the declarative import had re-exposed three of them
  under plain admin auth. They are refused on import now, and the litigation-hold
  setter gained the same step-up gate.
- **A webhook credential that shipped in clear text.** A bearer token or API key
  in a delivery destination's custom headers was missed by the redaction, so it
  appeared verbatim in the support bundle, the config export and the
  encrypted-backup redaction. Both redaction modes mask header values now.
- **A pre-auth device-existence oracle.** The network-appliance config-archive
  endpoint answered "not found" before it authenticated; it authenticates first
  now, like every sibling.
- **The threshold-impact preview** now lists the thresholds it could not assess
  instead of implying "no host changes state" means every change is safe — it
  recomputes the checks engine only, about seven of the ninety-odd parameters.
- **Alerts that could never clear**: three control-plane recovery events
  (maintenance-sweep, sidecar, audit-forward) hit a device-scoped guard and left
  their inbox alerts open forever; and a sweep alarm claimed "N times in a row"
  while counting cumulative failures. Both fixed.

The full write-up, with impact stated and no working inputs, is in
`docs/security-review-6.4.2.md`.

## Linux security posture reaches the tools that act on it

Host firewall state, sshd hardening and the automatic-update mechanism were
collected on every heartbeat and reached only the advisory list, which pages
nobody — while the Windows and macOS equivalents were already Checks-page rows.

- **Three new Linux check rows.** `linux_firewall` (no active nftables/iptables/
  ufw ruleset — and an unreadable probe is *not* flagged as off), `linux_ssh_
  hardening` (critical on permit-empty-passwords, warning on root password login
  or password authentication; key-only root is fine) and `linux_auto_update`.
- **Queryable fleet-wide.** New fleet-query facets `firewall_off`, `ssh_weak` and
  `autoupdate_off` answer "which hosts have no active firewall / permit root or
  password SSH / have automatic security updates off", in the query builder and
  the saved-query API.
- **PCI 1.2.1 attests host firewall state** instead of returning a blanket
  "cannot assess" — the product has reported it since v3.12.0 — while stating that
  upstream/network firewalls stay out of scope.
- **The declarative export stopped dropping what it claimed to cover.** The
  fleet-wide log-alert rules were exported from a config key nothing writes (an
  always-empty phantom) and now bind to their real store; and the operator
  suppression decisions `exposure_mutes` (muted world-exposed ports) and
  `compliance_baseline` (disabled compliance checks) are exported too, so a
  git-driven rebuild no longer silently restores them to alerting.

## Upgrading

Nothing to do beyond the usual upgrade and one hard reload. Container mutes are
stored in the existing `alert_mutes.json`, so no migration runs and an install
with no mutes is unchanged. The larger log tail needs an agent on 6.4.2 or
later; older agents keep working and return their 50-line default. The new Linux
posture check rows and query facets read data the agent already reports, so they
populate as soon as the server is on 6.4.2 — no agent change is required.

Two compatibility notes for anything consuming RemotePower from outside:

- **Webhook receivers need no change.** The new signature header is sent
  alongside the existing one, and the legacy header is byte-for-byte what it
  was. A receiver that wants replay protection should verify the new header —
  the worked example is in [webhooks.md](webhooks.md).
- **Prometheus per-device health changed labels.** The `device` label now
  carries the device id and the display name moved to a new `name` label.
  Dashboards and alert rules that matched on the name should move to `name`;
  anything joining across the other per-device series will start matching for
  the first time. The SLO budget and burn-rate gauges are omitted for monitors
  whose stored window is too short to resolve their target, rather than
  published as a flat 100 or 0.
