# RemotePower v7.2.0 — "Ev1denceMatters"

A release about evidence.

Threat intel used to learn about an attacker from failed SSH logins and a few
web patterns, and every report it filed said the same thing: brute force. Your
hosts already know much more than that. The web server logs every request, the
WAF records which rule fired, fail2ban and CrowdSec decide who to ban. Now
RemotePower reads those logs and a report says what the address actually did.

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v7.2.0`).

## The log sensor

Switch it on under **Security → Threat intel → Log sensor**. It is off until you
do, and it runs on Linux agents only.

Each agent then reads, read-only and once a minute, in a thread of its own:

- nginx and Apache access logs, for SQL injection, path traversal, code
  execution attempts, scans for exposed files and login brute force;
- nginx and Apache error logs, for ModSecurity messages, rate-limit trips and
  failed basic-auth logins;
- ModSecurity's audit log, native or JSON, for which rules fired and whether
  the WAF blocked the request;
- fail2ban's log, for who it saw failing and who it banned;
- CrowdSec's alerts for scenarios that fired on this host, AppSec included.

The agent finds the files from your web server's own configuration and reads
each in the layout its `log_format` declares, so a custom format works without
setup. A log it cannot read, or cannot understand, shows up on the new **Log
sources** card instead of quietly counting nothing.

What leaves the host is counts and a short list of fixed labels per address:
`SQL injection`, a WAF rule number, a CVE id the logs named, the name of a
fail2ban jail. Log lines, request paths, host names and user names stay on the
host, and the server drops anything that is not on its fixed list.

## What a report says now

- **The categories match what was seen.** SQL injection is filed as SQL
  injection, path traversal as path traversal, scanners as scanners. SSH brute
  force is filed as before.
- **One report per address, per service.** An address two hosts or two logs saw
  is one report. Before, the same attacker seen by two hosts in one sweep was
  reported twice to each service.
- **The wording comes from fixed phrases and numbers**, for example `SQL
  injection and path traversal: 41 attempts within 10 minutes, seen by web
  server log and WAF (reported by RemotePower)`. Nothing an attacker typed can
  reach a public report. You can still write your own message, and it can now
  use `{attack}` and `{seen_by}`.
- **The standard message no longer says "brute force" for everything.** It is one
  text for every report, `{attack}: {count} attempts within {minutes} minutes,
  seen by {seen_by} (reported by RemotePower)`, so "brute force" appears only when
  that is what the address did. The Settings box used to show the old wording,
  `{what} brute force: {count} failed attempts within {minutes} minutes`, which
  was wrong for most of what the logs find. The web counter's own reports now say
  `web login attempts and refused requests`, because it counts any 401 or 403.
- **AbuseIPDB is told when it happened.** For reports built from the logs, the
  time of the attack goes with the report.
- **A repeat is an answer.** If a service says it was reported moments ago, often
  by fail2ban on the same host, RemotePower counts it as done. SniffCat uses one
  status for a repeat and for its rate limit, but a repeat says so in its
  message and is read as one. Any other refusal is shown as "rate limited or
  already reported" and left alone for a little over its 20-minute window.

An address is reported when fail2ban banned it, when one of CrowdSec's own
scenarios raised a ban on this host, when the WAF refused it three times, or
when it made as many hostile requests as **Report after attempts** says. What
it does adds up for a day, so a slow attacker still counts. Community
blocklists and decisions made by hand are never evidence of an attack on you.

If fail2ban reports to the same services from the same account, turn its
reporting actions off once RemotePower does it. Leaving them on is harmless.

## What you can see

- The **Evidence** column shows what each address was seen doing and who already
  decided on it. **Details** opens the sources, the rule and CVE ids, and exactly
  what was sent to each service.
- **Log sources** lists every log each host's agent reads, how much of it was
  understood, and its state: reading, quiet, file missing, no permission, or not
  understood.
- The page says why an address has not been reported yet, for example
  `4 / 10 attempts so far`.

## Protections

- Cloudflare's published addresses are never queued, looked up or reported. A
  server that does not restore the visitor's address logs the proxy, and a
  report would have blamed it. The Log sources card says when this is
  happening, with the fix.
- A web attack that arrives through a proxy is not blocked on the host: the
  visitor's address is not the packet's source there, so the rule would block
  nothing.
- An agent sends at most 300 addresses at a time and a host can add 3,000 an
  hour, so one host cannot use up your day's reports.
- Network work is limited to 25 addresses a sweep, strongest first, so a short
  daily allowance goes to the addresses that earned it.
