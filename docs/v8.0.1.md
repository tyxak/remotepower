# RemotePower v8.0.1 — "L0gMatters"

A release about what Threat Intel tells you and what it does about it. Clear now empties the table, even with the Edge blocklist on. A service that
does not answer is no longer counted against your daily limits, and each service can have limits of its own. A new Request log shows what RemotePower
sent to AbuseIPDB and SniffCat, what each answered, and what your hosts' sensors sent, so a missing address can be traced. An address that fail2ban,
CrowdSec or a honeypot has already banned can be blocked without waiting for a reputation score, if you tick one box. It all came from one
installation: SniffCat answered every report with an error for a day, and RemotePower said its own limit was used up while SniffCat's page showed
none used.

## After you upgrade

- Hard-reload the dashboard once so the new front end loads.
- Update the Linux agents to get the sensor's log lines (see the Request log below), the request samples and the CrowdSec bouncer's refusals on AppSec's verdict. The Windows and macOS agents change in their version number only.
- **Request samples are sent by default.** Hosts now send up to three samples with an address: the method, the path without its query string, the status and which log. Until now no path left a host. Untick **Send up to three request samples with each address** in the **Log sensor** card on the **Settings** tab of Threat Intel to go back to counts and fixed labels only.
- No report carries a path until you tick **Add a few example requests to reports** in the **Limits and report message** card.
- **Reports name the kind of probing.** A report that said "probing for exposed files and admin pages" now says which kind it was when the source can
  tell, and some kinds are filed under one more category at AbuseIPDB and SniffCat. If your ignore list holds "probing", it still covers every kind.
  If your Cloudflare custom rules have vague descriptions, see [A report says what kind of probing it was](#a-report-says-what-kind-of-probing-it-was).
- **With the edge sources on, a zone that is read one event at a time is asked for three more fields**: the path, the method and the time of a
  refused request. The same box as for hosts switches it off.
- **Today's counts.** If a service was down, older versions counted its failed tries against your daily limits. The first time 8.0.1 runs it drops
  the day's report counts it did not write itself, and counts from then on only what a service answered, so nothing needs resetting by hand. The
  lookup counts stay.
- Nothing blocks differently until you tick **Also block addresses that fail2ban, CrowdSec or a honeypot has already banned**.
- **Run Scan all hosts once on the CVE page.** Rocky Linux, AlmaLinux, Red Hat and Alpine hosts get findings that were left out before, see
  [Vulnerabilities that were not shown](#vulnerabilities-that-were-not-shown). An updated Linux agent sends its package list again by itself,
  now with the source package of each package.
- **Debian and Ubuntu hosts get many new findings on that scan**, once their agent is updated: their libraries, their SSH server and their
  kernel are checked for the first time. Expect one `cve_found` for each such host if critical and high are among your alert severities. To
  hear only about what an update clears, tick **Only CVEs an update can fix, or that are known to be exploited** beside the severities of
  `cve_found` before you scan. See [Debian and Ubuntu are checked by source package](#debian-and-ubuntu-are-checked-by-source-package).

## Clear takes every address off the table

With the Edge blocklist on and **Found by RemotePower** at its defaults, nearly every address on an internet-facing installation qualifies for the
list. **Clear** used to leave each of those rows whole and answer "Kept because the edge blocklist uses them", so it removed almost nothing.
Those addresses leave the table now. The blocklist keeps each one's last sighting, score and reports in a row that names no host, so your Cloudflare
list does not shrink, and the row goes when the list would have dropped the address anyway. The answer says **Kept for the edge blocklist**.

## Each service has limits of its own

**Lookups per day**, **Reports per day** and **Blacklist downloads per day** can be set for AbuseIPDB and SniffCat separately, in the **Limits and
report message** card on the **Settings** tab of Threat Intel. A blank box uses the general number (900) and downloads use 4 a day, so nothing changes until you fill one in.
Use it when a plan allows more than the free one. The usage line under the boxes counts each service against its own limit. See
[Limits on API use](ip-intel.md#limits-on-api-use).

## A service that does not answer

A network failure or an HTTP 5xx from AbuseIPDB or SniffCat is no longer counted against **Lookups per day** or **Reports per day**. The address
waits ten minutes before that service is asked about it again, and a service that fails three times in a row in one pass is left alone for the rest
of that pass, so one that is down costs three requests and not one for every address waiting.

The Edge blocklist's blacklist downloads follow the same rule. A download that got no answer is not one of the day's four, and the source waits ten
minutes. See [Limits on API use](ip-intel.md#limits-on-api-use) and [Edge sources](edge-sources.md).

## See what was sent

The **Request log**, on the **Log sources** tab of Threat Intel, lists the last 150 lines. Some are requests to AbuseIPDB and SniffCat: the time,
the service, whether it was a lookup, a report or a blacklist download, the address, the HTTP status, how long it took and the service's own
sentence. The others are **Sensor reports**: what your hosts' log sensors sent, with the host, how many addresses were queued, held back or set
aside, and the first few. Keys, headers and the text of a report are never shown. Only the platform operator sees it, and deleting a host removes the
lines it made. The Linux agent also writes
a line to its log each time its sensor sends addresses, and a warning when a send or a pass fails. See [See what was sent](ip-intel.md#see-what-was-sent).

## Block what a ban engine already banned

A new scanner has no reputation yet, so an address that fail2ban banned in three jails was not blocked by RemotePower, because its score was below
the threshold. Tick **Also block addresses that fail2ban, CrowdSec or a honeypot has already banned, whatever their score** and such an address is
blocked on the host that saw it and, with the Edge blocklist on, banned at the edge. Behind Cloudflare the edge ban is the one that stops the
visitor. Everything that protects an address still applies, and the block says who decided: `automatic · fail2ban`.

The decision is made by software on your hosts, so a host you do not trust can get an address banned at the edge this way, up to the hourly cap.
Leave the box unticked if one of your hosts is not under your control. See
[Block what a ban engine already banned](ip-intel.md#block-what-a-ban-engine-already-banned).

## What an address asked for

An address that CrowdSec banned on an AppSec rule used to show "not reported: nothing recognisable in the logs": the sensor sent the decision and nothing about
the request. The sensor now keeps up to three samples for an address, and the details of the address list them next to the CrowdSec scenarios and the
rules that named it. The outcome line says what held a report up, for example "no attack category for the CrowdSec scenario ..." or "... the fail2ban jail
recidive", where it only said "nothing recognisable".

A sample is the method, the path, the status and which log. The path has no query string and no `;name=value` parameter, ends where a URL starts and at any
character other than letters, digits and `. _ ~ / % + -`, and is at most 80 characters. RemotePower rebuilds every sample from parts it checks itself,
so what an agent sends is never kept as it arrived, and the page escapes what it shows. See [What is sent](ip-intel.md#what-is-sent).

CrowdSec names the server could not class now have a category: the AppSec rules that protect an uploads folder from listing and from running PHP are
probing and code execution, `base-config` and `crs` are the WAF, and a few more, such as a Guacamole or a Cowrie honeypot login, have one.
A crawl is still not reported: an aggressive crawler is not an attack. The lines CrowdSec's nginx bouncer writes when it refuses a request on AppSec's
verdict count as WAF refusals, with the request they were about.

## A report says what kind of probing it was

A day of reports used to read as one sentence repeated: "probing for exposed files and admin pages", whether the address had asked for `.env`, for
phpMyAdmin or for a WordPress file, and whether a host, Cloudflare or the honeypot had seen it. Probing now has kinds, and a report names the kind
when the source can tell: configuration files, keys and backups; admin, login and debug pages; WordPress; user enumeration; an open proxy; private
host names; unusual HTTP methods; and files taken from the honeypot's fake backup directory or fake git repository. A source that can only say an
address was probing still uses the old sentence. A service's login has kinds too: RDP, SMB, Telnet and database logins are named.

Every source names the kind it can see. The Linux agent's sensor does for the requests in a web server's logs. Each honeypot trap has its own. A
CrowdSec scenario or a fail2ban jail is read by its name. A Cloudflare custom rule is read by its description, so say in it what the rule blocks
("sensitive files", "WordPress", "admin panels", "user enumeration", "unusual methods", "private hosts"). A rule whose description listed the files
it blocks, with `.sql` among them, used to be reported as SQL injection; it is read as a rule about files now.

Configuration files, keys and backups, and files taken from a decoy, are also filed as hacking (15 at AbuseIPDB, 11 at SniffCat). RDP, SMB and
Telnet brute force carry SniffCat's own category for each (22, 24 and 23).

In **Never report an address when all it did was**, the finer kinds sit under the general one. Ticking the general kind covers them, so a list that
ignored probing before this release ignores the same addresses now. See [What a report says](ip-intel.md#what-a-report-says).

## What Cloudflare refused and what the honeypot answered

Reports built from the edge sources had no examples, and their time window was the ten minutes RemotePower reads at a time. With **Send up to
three request samples with each address** ticked, RemotePower now keeps the method and path of up to three requests per address that Cloudflare
refused or your honeypot Worker answered, and uses the events' own times, so a report about one request says one minute and not ten. The
samples are cut the way a host's are, and a report carries them only when you tick **Add a few example requests to reports**.

This needs a zone that is read one event at a time, which is what a Free plan gets. The grouped view holds no request. If Cloudflare does not give a
field, RemotePower asks again without it and the Edge feeds card says what it got. RemotePower never asks Cloudflare for a query string, a host name
or a user agent. See [Edge sources](edge-sources.md).

The **Request log** shows the categories each report was filed under.

## Examples at the end of a report

**Add a few example requests to reports**, in the **Limits and report message** card, ends a report about a web attack with up to three of the requests the
logs showed, for example `Examples: GET /wp-login.php (404), POST /xmlrpc.php (403)`. It is off until you turn it on. A report about SSH, mail or another
login never carries examples, and neither does one about an address seen doing both. An address your own software banned by mistake would put a path from
your site on a public page, so look at the requests on the **Attackers** tab first. See
[Examples at the end of a report](ip-intel.md#examples-at-the-end-of-a-report).

## Uninstall agent says what happened

The Hosts page has a badge for a host whose agent was asked to uninstall, and it never showed: the list did not carry the mark it is drawn
from. It does now, and the badge follows the command. **agent uninstalling…** means the command waits for the host's next check-in, **agent
uninstall queued** means the host is offline and gets it when it reports again, and **agent uninstalled** means the heartbeat has handed the
command to the agent. The audit log no longer says an agent was reinstalled at the moment it was told to uninstall. If an agent still reports
five minutes after it was told, the badge goes and the audit log says `agent_reinstalled`: it was installed again, or the uninstall did not work.

## A notification destination that stopped working

If a webhook address is revoked or the mail server's password expires, deliveries fail and until now nothing said so: the alerts just
stopped arriving. RemotePower now raises an alert when a destination has failed three deliveries in a row, in the inbox and through every
other destination you have, and closes it when a delivery gets through again. A second destination, even a plain email, is what makes a
failing one reach you. See [A destination that keeps failing](webhooks.md#a-destination-that-keeps-failing).

## Vulnerabilities that were not shown

Three things kept findings off the CVE page, and one put findings on it that did not belong there.

- **Rocky Linux, AlmaLinux and Red Hat.** A package whose version has an epoch, such as `openssl` (`1:3.0.7`), showed no finding however old it
  was, because the check for "already patched" read the epoch of the fix as part of the version. A package with a high epoch, such as `bind`,
  kept every advisory after you updated it. Both are compared in RPM's own order now.
- **Alpine.** A fix that only raised the `-r` revision or the letter of a version (`1.1.1w` to `1.1.1x`) counted as installed. Alpine versions
  are compared in Alpine's own order now, and with an updated agent a library is checked as the package it was built from: `libcrypto3` and
  `libssl3` as `openssl`.
- **Rocky Linux and AlmaLinux hosts were shown advisories of other releases.** They are asked for with their major release now.
- **One failed request to OSV during a fleet scan** emptied the findings of every host until the next scan. A host whose scan fails now keeps
  its last findings.

Run **Scan all hosts** once after the upgrade, and expect the numbers to move: up on RPM and Alpine hosts that were behind on updates, down
where an RPM host showed one finding per installed package of the same source. A finding now carries the source package's name and lists the
installed packages after **installed as**.

## Debian and Ubuntu are checked by source package

A Debian or Ubuntu host was checked under the names of its installed packages, and the advisories are filed under the source package. So
`libc6`, `libssl3`, `openssh-server` and the kernel were never checked: a host that was a year behind on OpenSSH showed nothing for it. With an
8.0.1 agent these hosts are asked for by source package.

That brings the opposite problem. Debian and Ubuntu publish every known CVE of a release, fixed or not, and the kernel alone has more than a
thousand. So a scan lists a finding one by one when an update for the host's release clears it, when it is critical or high, or when it is
known to be exploited, at most 300 for a host and 50 for one package. Everything else is counted per package. The **Counted** column, a line
under the tiles and the host view show how many there are, of which severity and in which packages. See
[What is listed and what is counted](cve.md#what-is-listed-and-what-is-counted).

What else changes for these hosts:

- **An Ubuntu fix is read for the host's own release.** A finding used to name the fixed version of whichever release its advisory listed
  last. It now names the fix of the host's release, or says **Fixed in a newer release**, or **Fixed with Ubuntu Pro** when the fix ships
  there only. A fifth tile, **Needs Ubuntu Pro**, counts those.
- **A notice is not a second finding.** A DSA or a USN is left out when the records of its CVEs already tell the host to install a version at
  or past the notice's fix. A notice whose fix nothing else reaches stays.
- **Debian's "unimportant"** makes a finding low on a host of that release, whatever its CVSS score.
- **The first scan of such a host reads a few thousand advisory records**, eight at a time, in about two minutes. Later scans read only what
  is new or changed. The **CVE details cache** setting now only applies when OSV gives no change date.
- **Derivatives.** Pop!_OS is handled as Ubuntu. Linux Mint, Zorin OS and elementary OS report a version of their own, so their Ubuntu release
  is not known and they are still checked package by package. The host view says so.

Four things were found on the way and are fixed for every distribution:

- **KEV and EPSS matched nothing on Debian, Ubuntu, AlmaLinux and Rocky Linux findings.** Those advisories name their CVE in a field
  RemotePower did not read. The KEV badge shows after the next scan, the EPSS percentage after the next daily refresh of the feeds.
- **A remediation campaign over a list of CVE IDs, or over known-exploited findings, matched nothing** and was marked completed by its first
  daily sample. It matches by a finding's ID and aliases now, and reopens with the next sample if hosts are affected.
- **The MCP tool `get_cves` failed for every host name**, in the hosted endpoint and in the sidecar. It asked for a path that does not exist.
- **An SBOM vulnerability pointed at no component** when its finding is filed under a source package. It points at every installed package
  built from that source now.

A changed CVSS cut-off under **Forecast & CVE tuning** now applies to every finding at the next scan. The host drawer no longer calls a host
clean when it was never scanned or when its scan only has a count.
