# RemotePower v6.4.3 — "Gu4rdMatters"

A release about the checks rather than the code they check.

Six guardrails turned out to be reporting success while measuring nothing. The
Postgres backend — the enterprise default since v6.1.0 — was run by no gate at
all, while 28 tests written for it sat in the tree skipping themselves for want
of a server. `ruff --select F821`, the check that catches a typo'd name no
amount of source-text assertion can, was returning 238 findings on the server
of which every single one was a false positive. The accessibility sweep walked
all 74 pages against an empty database, so anything that only exists once there
are rows was invisible to it. The translation gate stopped at the app chrome.
The box-overflow ratchet read only static HTML, and counted a compliant table
against its own budget.

Alongside them, a set of surfaces that told the operator something untrue.

Every new guardrail here was demonstrated to FAIL before it was committed. A
gate nobody has watched fail is indistinguishable from one that cannot.

That principle then paid for itself. Three more blind spots turned up while
closing the list, and each was found by a check being made to work rather than
by anyone reading the code: the translation gate had never looked at the
attributes a screen reader announces, the accessibility audit had never opened
a dialog, and a test counting database writes could not see them on two of the
three backends — so four of its assertions were passing while measuring
nothing, in a file written to catch exactly that.

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v6.4.3`).

## Checks that now check something

- **Postgres is in the gate.** CI runs the backend suite against a real
  throwaway database, configured so an unreachable server fails the build
  rather than quietly skipping. Three backend parity bugs had already reached
  releases, one of them recorded in the source as impossible to catch locally.
- **Undefined-name detection works on the server again.** The 513 names bound
  in at runtime are declared, so the check reports real problems instead of
  noise, and it runs over all shipped server, agent and sidecar code — plus the
  test suite, where a typo in a rarely-taken branch hides best.
- **Accessibility is audited with data on the page.** A seeded pass covers what
  the empty-install sweep structurally cannot see.
- **Dropdown options, column headers and field labels are translated**, and the
  strings that are deliberately English — brand names, protocol tokens, enum
  values — are recorded as such instead of being indistinguishable from ones
  nobody got to.
- **Test pins stop guessing how long the code is.** 91 assertions sliced a
  hardcoded number of characters from an anchor, which silently stops covering
  its target as the code grows — and with a negative assertion, silently passes
  while checking nothing.

## Things that were telling you something untrue

- A green "queued" toast on an action the server had already refused, at eleven
  places.
- The Documentation page denying a restore feature that ships, and steering you
  to the manual procedure — the one that does not take a safety snapshot first.
- Enrollment PINs documented as single-use that were not.
- Push notifications rendering `?` where a character should be.
- Two pages destroying their own Documentation link a moment after you opened
  them.
- The literal word `undefined` rendered into headings and summaries when a
  record was missing or access refused.

## Actions that did nothing

The macOS agent implements seven of the eighteen commands the server can send
it; the Windows agent implements fourteen. Everything else was queued, handed
over, and answered `unsupported command` into a result row nobody reads — so
the button worked, the toast was green, and the machine did nothing. The server
now knows which agent implements which command and refuses the rest at the
door, naming the platform and the gap. A mixed-platform batch reports the hosts
it skipped instead of counting them as successes.

The same shape appeared in five features that set a one-shot flag only the
Linux agent reads: the container-image CVE scan (which auto-targeted every host
reporting containers, including Windows), the infrastructure-as-code collector
(which then blamed the agent for a three-minute timeout), on-host `lynis`
audits (queued, marked *running*, and left there until the reaper timed them
out an hour later), ACME certificate rescans, and DNS credential import. Each
now refuses up front.

And in two places the server had *already* been refusing honestly since v6.4.2
— host config saved against a Windows or macOS host, and a file-backup job with
non-Linux targets — while the interface discarded the answer and showed success
anyway. Both now say what actually happened. A file-backup job could also be
pointed at a Windows host by *editing* it, which skipped the check the create
path performs; that gap is closed, and the edit reports its skipped hosts the
way creation always did.

Separately, the three agents had drifted on how much of a server response they
would read: 1 MB on Linux, 4 MB on Windows, and **unbounded** on macOS. All
three now share one pair of limits.

## Signals that were collected and thrown away

A field the agent sends that the server's whitelist does not name is dropped
silently, and everything downstream behaves as though it were never sent. Four
had been in that state:

- **The host's own hostname.** Reported in the heartbeat by the Windows and
  macOS agents and then dropped; the Linux agent — most of a typical fleet —
  did not send it at all outside enrolment. Either way the stored value was
  whatever the machine was called when it enrolled. Rename a host and the old
  name stayed on the drawer, in alert payloads, and in the topology matching
  that resolves neighbours *by* hostname. The display name you chose is still yours — a host cannot rename
  itself in the interface.
- **Whether the agent has `psutil`.** The Windows and macOS agents say so
  explicitly when it is missing. That answer was discarded, so three empty
  states could only guess, and told you to go and check a dependency the agent
  had already reported on.
- **`X11Forwarding` from the sshd config.** Collected, stored, read by nothing.
  It now appears in the SSH hardening check — advisory, not critical, because
  plenty of workstations enable it deliberately.
- **Who a privileged command actually ran as.** The sudo trail parsed and
  stored the effective user all along, and both tables showed only who invoked
  it, so `sudo -u backup` and `sudo -i` looked identical in an access review.
  There is now a "Ran as" column, and the AI advisor's grounding says it too.

The LLDP topology card had a related problem: it can only suggest a link
between two *enrolled* devices, and LLDP mostly finds switches, routers and
access points, which are not enrolled. Those were discarded without a word,
and the empty card advised installing lldpd — on a fleet where lldpd was
installed and working. It now reports how many neighbours were seen and why
none of them can appear here.

## Installing on RHEL and Arch

The app server and the maintenance scheduler could not start there. Both units
ship `User=www-data`, the Debian web-user name, and the installer was rendering
the distro's actual web user into only one of the three units it installs — so
systemd refused both with `status=217/USER`. The data directory is owned by the
distro user either way, so hand-creating a `www-data` account would not have
helped. Debian and Ubuntu installs were unaffected.

## Thermal health

The Thermal page has been given room to work: the sensor table is no longer
capped at a fraction of the viewport, and expanding a host gives the per-sensor
detail and the temperature timeline a usable amount of screen instead of a
sliver you had to scroll inside a scroll.

The page also stops being fooled by a dead board sensor. A reading that is
exactly the ADC's open-circuit rail — 127 °C or −128 °C, or anything outside
−40…150 °C — is not a measurement, and is now discarded as it arrives. A sensor
reading past its own critical limit on a host that is otherwise perfectly
healthy is a different case: it is *probably* an unconnected pin, and
"probably" is the wrong confidence at which to silently stop alerting on a
machine that might genuinely be cooking. Those are flagged **Implausible** and
left alone, with one click to ignore that sensor on that host. An ignored
sensor stops driving the page headline, the `temp_high` alert, the overheating
risk factor and the roll-up maximum — because until now a single dead pin drove
all four.

## Things you were never told about

The forecast that projects when a disk fills has raised an alert for eight
releases. The same projection for **memory, swap and CPU load** shipped in
v6.4.2 and reached nothing at all — no alert, no attention item, no check. A
host projected to exhaust its memory in three days was visible only if you
opened that one device's drawer and scrolled to the forecast card. It raises an
alert now, per resource, so a host saturating memory and swap gets two and
clearing one does not silence the other. The ceilings it projects against are
tunable on Settings → Alert parameters — the forecast has accepted those
overrides since it shipped and nothing ever passed them.

A **NetFlow exporter that stops sending** is noticed rather than frozen in
place, and one healthy router no longer masks every dead one.

## Compliance and encryption

The encryption-at-rest control read BitLocker on Windows and FileVault on
macOS, and nothing on Linux — so an all-Linux fleet, which is most of them, saw
**"not assessed" permanently** on a SOC 2 / ISO / PCI control no amount of
actual encryption could satisfy. The agent now reports dm-crypt / LUKS state,
and it reaches the Checks page, both fleet reports and the control itself.

A host that cannot see device-mapper still reports nothing rather than
"unencrypted". Being unable to look is not the same as looking and finding
nothing, and treating it as a finding would fail hosts that are in fact
encrypted.

## Accessibility

The translation gate covered the visible chrome. It had never looked at
`placeholder`, `title` or `aria-label` — the strings a screen reader actually
announces — so **1,081 of them had accumulated in English** while the engine
that translates them worked perfectly. The chrome a keyboard user meets on
every page is translated now; the rest is recorded exactly so it can only
shrink. It stays a recorded backlog on purpose: about a third of those strings
are example DATA you copy, like a cron line or a log path, where translating
would be actively wrong.

The accessibility audit walked every page and every Settings pane and **never
opened a dialog** — and there are 138 of them, each hidden until something
opens it, which the audit tool does not scan at all. Modals are where the forms
are, so that was the surface where it mattered most. The first thing the new
walk found: confirmations and prompts are labelled by their title element, and
that title was empty unless the caller passed one, which **143 callers did
not**. Most confirmations in the product announced themselves to a screen
reader as "dialog" and nothing more. Both now default to a real title.

A field marked invalid is also visible now — the attribute was being set for
screen readers with no styling behind it, so a sighted operator saw nothing.

## Hardware and homelab

Monitoring your disks stopped keeping them awake. SMART polling **spun up every
sleeping drive** on every hardware cycle to ask whether it was healthy, which
defeats spin-down completely and spends power and start/stop cycles on exactly
the archive arrays whose owners configured spin-down on purpose. The disks are
left asleep and the table says "asleep" rather than showing a blank row that
reads like a fault.

Four signals that had no source: **Raspberry Pi under-voltage and thermal
throttling** — the commonest cause of "my Pi is randomly unstable" and
invisible in every other metric — plus fan RPM, the CPU frequency governor, and
wireless link quality. All read straight from the kernel, so nothing needs
`vcgencmd`, `sensors` or `iwconfig` installed.

Only the throttling one raises a status. A fan reading 0 RPM is usually an
empty header, and `powersave` is the default governor on most distributions;
warning about either would cry wolf on healthy hardware.

## Settings that did not save what you typed

The Alert parameters page carries 92 numeric thresholds, and anything that did
not parse as a number was **silently replaced by the value RemotePower ships
with** — then reported as saved. Clearing a field was wrong in the other
direction: instead of removing your override so the default applies again, it
stored the default as an explicit override, quietly pinning the old number the
next time that default moves. Bad input now stops the save and says which field;
a cleared field clears the override on every tunable rather than the two-thirds
that already did.

## Security

A review of this release found three fleet-wide read endpoints that
authenticated the caller and then answered as though every caller were an
unrestricted administrator — the metrics endpoint, the calendar feed and the
rack elevation view. All three are read paths exposing no credential or
command channel, all three predate this release, and all three are fixed here.
See [security-review-6.4.3.md](security-review-6.4.3.md).

A later pass found a fourth, and this one is a WRITE path rather than a read.
On a multi-tenant install, a user created by OIDC, SAML, SCIM or LDAP was
stamped with **no tenant** — and a user with no tenant belongs to the built-in
default one, where an admin can see *every* tenant. So an identity-provider
group mapped to `admin` silently produced cross-tenant access, and there was no
setting anywhere that could express "admin **of** this customer".

There is one now (Settings → Security → *Tenant for SSO-provisioned users*),
and until it is set RemotePower creates that account as a viewer rather than
guessing, recording in the audit log what it did and why. Every earlier fix in
this area hardened a path that READS; this one was creating the account wrong,
after which every read behaved correctly.

**If you run a single organisation, none of this applies to you** — tenancy is
off by default, and the tenant now stamped is the one those accounts already
resolved to.

## Things only a browser could see

Four defects in this release were found by rendering the product and measuring
it, not by reading it — in every case the source is correct on its own terms.

The device list wrapped itself in a scroll container only above **twenty** rows,
while the rule the rest of the product follows is about fifteen. Any fleet
between those numbers rendered a table five rows past the cap. Three separate
copies of that threshold existed and all three disagreed with the documentation;
they are one value now.

Twenty-four buttons disagreed with the other 289 about a single pixel of
icon-to-label spacing. A class set on the icon itself still carried a margin
from before the layout used gaps, so inside a button that now supplies its own
gap the two stacked; two other classes simply declared a different number; one
control was never a flex row at all; and two put their label on its own line in
the source, so the indentation rendered. It is 315 of 317 at exactly the same
gap now, and the gap is measured on every page rather than asserted in a
stylesheet.

Updating the bundled API-reference viewer rendered that page completely blank on
the first attempt: the page pins integrity hashes for the file, so replacing it
without recomputing them made the browser refuse the resource outright. A
file-level comparison showed a perfect update. Every integrity pin in every page
is now checked against the file it pins.

And the demo seeder did not populate this release's own signals, so a demo
instance showed the new Checks rows, the compliance control and the fleet-search
answers with nothing behind them — the pages rendered, the empty states did not
explain why, and a reviewer would reasonably conclude the features were broken.

## Fleet search can answer more questions

Of the fifty-five host signals the server keeps, twenty-one were named nowhere
in the fleet-knowledge index. Disk encryption and platform health — both shipped
in this release — were among them, so "which hosts are unencrypted?" could not
be answered from fleet knowledge while the Checks page displayed the answer.

Seven families are now indexed: Linux disk encryption and its encrypted mounts,
platform health (throttling, fans, wireless signal), a tripped canary file,
Integrity Guard quarantine counts, sshd configuration, signed-in users and
chassis type. An unencrypted host renders as such, so the question that matters
returns something; a host that cannot see its own device-mapper renders nothing
rather than a guess; and a secret-looking configuration field is never embedded,
because with a cloud embedding provider the index leaves the machine.

The remaining fourteen are excluded deliberately and say why — per-process and
per-interface counters change on every heartbeat and would re-embed the host's
entry for no retrieval value.

## A sweep of every page can now be run in minutes

The release adds three measurements that walk the running product rather than
its source: rendered box heights on every page, icon-to-label spacing on every
button, and integrity pins on every served page. They boot the real stack
against demo data, which is also why the seeder gap above mattered — two
existing gates already measured that instance and could not see what it never
contained.

## Upgrade notes

Nothing to do beyond the usual upgrade and one hard reload. No configuration
or schema changes.

**Three API behaviour changes**, all of them things that previously answered
with a success they had not earned.

From the security work above: `GET /api/metrics` and `GET /api/schedule.ics`
now return only the devices the CALLING SESSION is entitled to see. A Prometheus
scrape authenticating with the status token is unaffected and still receives the
whole instance — that is what the token is for. If you scrape with a user
session instead, point it at the status token.

From the SSO work above, and **only on installs with multi-tenancy
enforced**: if an identity-provider group maps to `admin` and you have not set
a tenant for SSO-provisioned users, newly created accounts are made viewers
instead of admins, and the audit log says so by name. Existing accounts are
untouched. Set the field — to `default` if a platform-wide operator is
genuinely what you want — to restore the mapped role.

From the platform work described under *Actions that did nothing*: an action
whose agent cannot perform it is now **refused** rather than accepted. Queueing
a Linux-only command at a Windows or macOS host returns `409` naming the gap;
an on-host `lynis` audit, an IaC collection, an ACME rescan or a DNS credential
import against a non-Linux host returns `400`. Nothing that used to work stops
working — these are all requests that were already producing no effect, and the
only change is that you now find out immediately instead of never.
