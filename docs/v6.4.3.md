# RemotePower v6.4.3 — "Gu4rdMatters"

A release about the checks rather than the code they check.

Six guardrails turned out to be reporting success while measuring nothing. The
Postgres backend — the enterprise default since v6.1.0 — was run by no gate at
all, while 28 tests written for it sat in the tree skipping themselves for want
of a server. `ruff --select F821`, the check that catches a typo'd name no
amount of source-text assertion can, was returning 238 findings on the server
of which every single one was a false positive. The accessibility sweep walked
all 74 pages against an empty database, so anything that only exists once there
are rows was invisible to it. The translation gate stopped at the app chrome.
The box-overflow ratchet read only static HTML, and counted a compliant table
against its own budget.

Alongside them, a set of surfaces that told the operator something untrue.

Every new guardrail here was demonstrated to FAIL before it was committed. A
gate nobody has watched fail is indistinguishable from one that cannot.

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v6.4.3`).

## Checks that now check something

- **Postgres is in the gate.** CI runs the backend suite against a real
  throwaway database, configured so an unreachable server fails the build
  rather than quietly skipping. Three backend parity bugs had already reached
  releases, one of them recorded in the source as impossible to catch locally.
- **Undefined-name detection works on the server again.** The 513 names bound
  in at runtime are declared, so the check reports real problems instead of
  noise, and it runs over all shipped server, agent and sidecar code — plus the
  test suite, where a typo in a rarely-taken branch hides best.
- **Accessibility is audited with data on the page.** A seeded pass covers what
  the empty-install sweep structurally cannot see.
- **Dropdown options, column headers and field labels are translated**, and the
  strings that are deliberately English — brand names, protocol tokens, enum
  values — are recorded as such instead of being indistinguishable from ones
  nobody got to.
- **Test pins stop guessing how long the code is.** 91 assertions sliced a
  hardcoded number of characters from an anchor, which silently stops covering
  its target as the code grows — and with a negative assertion, silently passes
  while checking nothing.

## Things that were telling you something untrue

- A green "queued" toast on an action the server had already refused, at eleven
  places.
- The Documentation page denying a restore feature that ships, and steering you
  to the manual procedure — the one that does not take a safety snapshot first.
- Enrollment PINs documented as single-use that were not.
- Push notifications rendering `?` where a character should be.
- Two pages destroying their own Documentation link a moment after you opened
  them.
- The literal word `undefined` rendered into headings and summaries when a
  record was missing or access refused.

## Interface corrections

- The rule meant to space a button's icon from its label matched none of the
  ~195 buttons that have both.
- The four sign-in buttons stacked at three different heights.
- The CMDB asset Tickets panel rendered 110px of content inside a 38px sliver.
- Every card on the Documentation page had its summary shattered into columns.
- Keyboard focus is visible in text fields again.
- A refused delete no longer stays deleted in memory.
- The Devices page no longer paints a blank body while it loads.

## Security

A review of this release found three fleet-wide read endpoints that
authenticated the caller and then answered as though every caller were an
unrestricted administrator — the metrics endpoint, the calendar feed and the
rack elevation view. All three are read paths exposing no credential or
command channel, all three predate this release, and all three are fixed here.
See [security-review-6.4.3.md](security-review-6.4.3.md).

## Upgrade notes

Nothing to do beyond the usual upgrade and one hard reload. No configuration
or schema changes.

**One API behaviour change**, from the security work above: `GET /api/metrics`
and `GET /api/schedule.ics` now return only the devices the CALLING SESSION is
entitled to see. A Prometheus scrape authenticating with the status token is
unaffected and still receives the whole instance — that is what the token is
for. If you scrape with a user session instead, point it at the status token.
