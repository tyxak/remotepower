# RemotePower v6.4.3 — "Gu4rdMatters"

A release about the checks rather than the code they check.

Six guardrails turned out to be reporting success while measuring nothing. The
Postgres backend — the enterprise default since v6.1.0 — was run by no gate at
all, while 28 tests written for it sat in the tree skipping themselves for want
of a server. `ruff --select F821`, the check that catches a typo'd name no
amount of source-text assertion can, was returning 238 findings on the server
of which every single one was a false positive. The accessibility sweep walked
all 74 pages against an empty database, so anything that only exists once there
are rows was invisible to it. The translation gate stopped at the app chrome.
The box-overflow ratchet read only static HTML, and counted a compliant table
against its own budget.

Alongside them, a set of surfaces that told the operator something untrue.

Every new guardrail here was demonstrated to FAIL before it was committed. A
gate nobody has watched fail is indistinguishable from one that cannot.

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v6.4.3`).

## Checks that now check something

- **Postgres is in the gate.** CI runs the backend suite against a real
  throwaway database, configured so an unreachable server fails the build
  rather than quietly skipping. Three backend parity bugs had already reached
  releases, one of them recorded in the source as impossible to catch locally.
- **Undefined-name detection works on the server again.** The 513 names bound
  in at runtime are declared, so the check reports real problems instead of
  noise, and it runs over all shipped server, agent and sidecar code — plus the
  test suite, where a typo in a rarely-taken branch hides best.
- **Accessibility is audited with data on the page.** A seeded pass covers what
  the empty-install sweep structurally cannot see.
- **Dropdown options, column headers and field labels are translated**, and the
  strings that are deliberately English — brand names, protocol tokens, enum
  values — are recorded as such instead of being indistinguishable from ones
  nobody got to.
- **Test pins stop guessing how long the code is.** 91 assertions sliced a
  hardcoded number of characters from an anchor, which silently stops covering
  its target as the code grows — and with a negative assertion, silently passes
  while checking nothing.

## Things that were telling you something untrue

- A green "queued" toast on an action the server had already refused, at eleven
  places.
- The Documentation page denying a restore feature that ships, and steering you
  to the manual procedure — the one that does not take a safety snapshot first.
- Enrollment PINs documented as single-use that were not.
- Push notifications rendering `?` where a character should be.
- Two pages destroying their own Documentation link a moment after you opened
  them.
- The literal word `undefined` rendered into headings and summaries when a
  record was missing or access refused.

## Actions that did nothing

The macOS agent implements seven of the eighteen commands the server can send
it; the Windows agent implements fourteen. Everything else was queued, handed
over, and answered `unsupported command` into a result row nobody reads — so
the button worked, the toast was green, and the machine did nothing. The server
now knows which agent implements which command and refuses the rest at the
door, naming the platform and the gap. A mixed-platform batch reports the hosts
it skipped instead of counting them as successes.

The same shape appeared in five features that set a one-shot flag only the
Linux agent reads: the container-image CVE scan (which auto-targeted every host
reporting containers, including Windows), the infrastructure-as-code collector
(which then blamed the agent for a three-minute timeout), on-host `lynis`
audits (queued, marked *running*, and left there until the reaper timed them
out an hour later), ACME certificate rescans, and DNS credential import. Each
now refuses up front.

And in two places the server had *already* been refusing honestly since v6.4.2
— host config saved against a Windows or macOS host, and a file-backup job with
non-Linux targets — while the interface discarded the answer and showed success
anyway. Both now say what actually happened. A file-backup job could also be
pointed at a Windows host by *editing* it, which skipped the check the create
path performs; that gap is closed, and the edit reports its skipped hosts the
way creation always did.

Separately, the three agents had drifted on how much of a server response they
would read: 1 MB on Linux, 4 MB on Windows, and **unbounded** on macOS. All
three now share one pair of limits.

## Signals that were collected and thrown away

A field the agent sends that the server's whitelist does not name is dropped
silently, and everything downstream behaves as though it were never sent. Four
had been in that state:

- **The host's own hostname.** Reported in the heartbeat by the Windows and
  macOS agents and then dropped; the Linux agent — most of a typical fleet —
  did not send it at all outside enrolment. Either way the stored value was
  whatever the machine was called when it enrolled. Rename a host and the old
  name stayed on the drawer, in alert payloads, and in the topology matching
  that resolves neighbours *by* hostname. The display name you chose is still yours — a host cannot rename
  itself in the interface.
- **Whether the agent has `psutil`.** The Windows and macOS agents say so
  explicitly when it is missing. That answer was discarded, so three empty
  states could only guess, and told you to go and check a dependency the agent
  had already reported on.
- **`X11Forwarding` from the sshd config.** Collected, stored, read by nothing.
  It now appears in the SSH hardening check — advisory, not critical, because
  plenty of workstations enable it deliberately.
- **Who a privileged command actually ran as.** The sudo trail parsed and
  stored the effective user all along, and both tables showed only who invoked
  it, so `sudo -u backup` and `sudo -i` looked identical in an access review.
  There is now a "Ran as" column, and the AI advisor's grounding says it too.

The LLDP topology card had a related problem: it can only suggest a link
between two *enrolled* devices, and LLDP mostly finds switches, routers and
access points, which are not enrolled. Those were discarded without a word,
and the empty card advised installing lldpd — on a fleet where lldpd was
installed and working. It now reports how many neighbours were seen and why
none of them can appear here.

## Installing on RHEL and Arch

The app server and the maintenance scheduler could not start there. Both units
ship `User=www-data`, the Debian web-user name, and the installer was rendering
the distro's actual web user into only one of the three units it installs — so
systemd refused both with `status=217/USER`. The data directory is owned by the
distro user either way, so hand-creating a `www-data` account would not have
helped. Debian and Ubuntu installs were unaffected.

## Thermal health

The Thermal page has been given room to work: the sensor table is no longer
capped at a fraction of the viewport, and expanding a host gives the per-sensor
detail and the temperature timeline a usable amount of screen instead of a
sliver you had to scroll inside a scroll.

The page also stops being fooled by a dead board sensor. A reading that is
exactly the ADC's open-circuit rail — 127 °C or −128 °C, or anything outside
−40…150 °C — is not a measurement, and is now discarded as it arrives. A sensor
reading past its own critical limit on a host that is otherwise perfectly
healthy is a different case: it is *probably* an unconnected pin, and
"probably" is the wrong confidence at which to silently stop alerting on a
machine that might genuinely be cooking. Those are flagged **Implausible** and
left alone, with one click to ignore that sensor on that host. An ignored
sensor stops driving the page headline, the `temp_high` alert, the overheating
risk factor and the roll-up maximum — because until now a single dead pin drove
all four.

## Security

A review of this release found three fleet-wide read endpoints that
authenticated the caller and then answered as though every caller were an
unrestricted administrator — the metrics endpoint, the calendar feed and the
rack elevation view. All three are read paths exposing no credential or
command channel, all three predate this release, and all three are fixed here.
See [security-review-6.4.3.md](security-review-6.4.3.md).

## Upgrade notes

Nothing to do beyond the usual upgrade and one hard reload. No configuration
or schema changes.

**Two API behaviour changes**, both of them things that previously answered
with a success they had not earned.

From the security work above: `GET /api/metrics` and `GET /api/schedule.ics`
now return only the devices the CALLING SESSION is entitled to see. A Prometheus
scrape authenticating with the status token is unaffected and still receives the
whole instance — that is what the token is for. If you scrape with a user
session instead, point it at the status token.

From the platform work described under *Actions that did nothing*: an action
whose agent cannot perform it is now **refused** rather than accepted. Queueing
a Linux-only command at a Windows or macOS host returns `409` naming the gap;
an on-host `lynis` audit, an IaC collection, an ACME rescan or a DNS credential
import against a non-Linux host returns `400`. Nothing that used to work stops
working — these are all requests that were already producing no effect, and the
only change is that you now find out immediately instead of never.
