# RemotePower v7.0.1 — "C0llapseMatters"

A patch release with one subject: the left sidebar collapses when you ask it
to. Both faults were reported from the field within a day of v7.0.0, and both
lived in how the sidebar works out its own width.

## Open alerts held the sidebar open, in every mode

RemotePower keeps the sidebar visible while something needs attention, so a
slim rail cannot conceal a problem. That rule matched on the collapsed state
alone — and a sidebar you collapsed by hand is in that same state.

So with a single alert open, clicking **Collapse** slid the page content across
to the narrow-rail margin while the sidebar stayed at full width on top of it.
The content moved and the menu did not, which is a strange thing to look at and
an easy thing to mistake for a rendering glitch. Turning auto-hide off changed
nothing, because that setting was never part of the check.

The reveal now applies only in auto-hide mode. Collapse works whenever the
button is there.

### New option: keep hiding while alerts are open

If you work with alerts open most of the day, the reveal is more nuisance than
safeguard. **My Account → Appearance → Navigation** has a second checkbox,
*Keep hiding while alerts are open*, which leaves the rail hidden regardless.

It is off by default, so nothing changes unless you ask for it, and like the
auto-hide switch itself it is remembered per browser rather than per account.

## Between 721 and 768 pixels, the button did nothing

Below 721 pixels the sidebar is a slide-over drawer, where collapsing has no
meaning, so the button is hidden. Above that it appears — but the rules it
drives began at 769 pixels, a floor left behind when the drawer breakpoint
moved from 768 to 720. In the 48 pixels between, you got a button and no
behaviour: no rail, no change to the content margin, nothing.

The gap was known and half-closed. A copy of the whole block, scoped to the
installed app, fixed it there and left the browser as it was. Two copies of the
same rules at two widths is how one of them came to be fixed on its own; there
is one copy now, and it starts at the width where the button appears.

## How this was checked

Both faults existed only as geometry — every rule involved reads as correct on
its own — so the tests measure a real browser rather than the stylesheet. They
check the sidebar width **and** the content margin at 730, 760, 780 and 1280
pixels, across auto-hide, manual collapse, the new opt-out, and alerts open
versus cleared.

Each test was watched failing against the old rules before it was kept. The
failure reads `248 != 56` with the content already at 56 — the overlap the
report described.

## Upgrading

Nothing to migrate, and no configuration changes. The browser caches a new
bundle on first load after the upgrade.

Thanks to **@loryanstrant** for the report (#27), and for mentioning that it
depended on window width — that is what turned up the second fault.
