# RemotePower v7.4.3 — "M3asureMatters"

The next batch of requests from the same Docker install. More of what the fleet already knows is measured
and alerted on, and a few rough edges of the HTTP monitors are gone.

After upgrading, hard-reload the dashboard once so the new front-end loads. Update the Linux agents to get
the disk figures; the other changes are on the server.

## How busy each disk is

The agent reported network traffic per interface and nothing about disks, so on a host with eleven drives
behind a controller and a RAID mirror you could not tell which drive was saturated or slow. The Linux agent
now reads the kernel's disk counters and sends, for each whole disk and each RAID array, the share of the
interval it was busy, the read and write rate, the requests per second and the average wait. Partitions,
logical volumes, loop, RAM and optical drives are left out, so a volume is not counted twice with its disk.

Open the host, go to the **Audit** tab, expand **Health & hardware** and look at **Disk I/O**. Each disk has a
row with an hour of trend, and a disk you named (below) shows its name.

A drive pinned at 100% for minutes often shows before SMART changes. Set the lines under **Settings → Alert
parameters → Disk activity**: *Disk busy warn %* and *Disk busy crit %* (both off at 0) and *Reports in a row*
(5). A disk has to stay over a line for that many reports in a row, so a scrub or a backup that pins it for one
minute does not alert. A host can have its own lines under **Metric thresholds** in its menu. You get one alert
for each disk. It closes when the disk calms down, when you turn the line off and when the disk is no longer
reported. See [disk-health.md](disk-health.md).

## A drive can have a name

On a host with eleven drives, several of the same model, `sdd` means nothing at a glance, and the letters change
after a reboot or a controller change. The Hardware tab has a **Disk names** box under the SMART table. The name
is kept against the drive's serial number, so it follows the drive whatever its letter. It shows in the SMART
table, on Predictive Health, in the *SMART failure* and *Disk predicted to fail* alerts, in Needs attention and
in the Disk I/O table, always next to the letter and the serial. A disk that reports no serial number cannot be
named. See [disk-health.md](disk-health.md).

## CPU and memory lines for containers

The agent has always collected CPU and memory per container, and the only container alerts were a stop and a
restart loop. You can now set a line for docker's CPU figure (100 is one core), for the share of a container's
memory limit and for memory in MB. A container has to stay at or over a line for a number of reports in a row (3
unless you change it), so a spike does not alert. The alert opens once for each container and resource, and
closes when the container drops under the line, stops, is excluded or the line is turned off. Nothing alerts
until you set a line.

Lines are fleet-wide (**Monitoring → Tuning → Container CPU and memory lines**), per host (**Lines for this
host** in its Containers section) and per container, matched by name or by `image:` like the exclude list. The
most specific one wins. The host's Containers view colours a reading that is over its line and draws a CPU and a
memory trend from the last 60 reports. A container using more than one core used to be clamped to 100%; it
keeps up to 6,400% now. See [containers.md](containers.md).

## A maintenance window can raise no alerts at all

A window held the notifications and still raised the alert, so a nightly backup that stops and starts 17
containers put 17 *Container stopped* alerts on the dashboard and in the alert history every night. The window
form has a new setting, **While the window is active**: *Hold notifications only* (every existing window, and
the default) or *Raise no alerts at all*. With the second, an event the window covers is not written to the
Alerts inbox and is left out of Needs attention and the stopped-containers count, so it stays out of the health
score too. Each one is still listed in the suppression log.

An alert that was open before the window starts stays open, and a recovery inside the window still closes it. A
problem that begins inside the window and is still there at the end shows in Needs attention again, but no alert
is raised for it later.

The window form could not save a site, a tag or a smart group as the target: it read the target text only for a
group. It can now. See [maintenance.md](maintenance.md).

## HTTP monitors

- **Expected status.** An app behind a login answers 401 at its root, and the expected status could not be set
  to 401. An expected status now decides alone, for every status; with none set, below 400 is up as before.
- **A monitor you edit while it is down closes its alert.** Editing a down monitor to a working target (adding
  `/ping`, say) left its alert open until someone resolved it by hand. The recovery matches the monitor by its
  label now, and deleting or renaming a down monitor closes its alert when you save.
- **Method.** *Auto* (every existing monitor) sends HEAD and tries GET once when HEAD is answered with 404, 405
  or 501. *HEAD* and *GET* send only that one. Home Assistant answers HEAD with 405, so it read as down while it
  worked.
- **Verify TLS.** A monitor can skip the certificate check, for a service on a self-signed certificate. The
  protocol floor and the address guard stay on.

Method and Verify TLS are in the monitor export and import, and an Uptime Kuma import carries over *Ignore
TLS/SSL errors*. See [monitors.md](monitors.md).

## An integration that reads Prometheus

Many homelab hosts export metrics in the Prometheus format, and some can only be monitored that way. The Custom
HTTP probe could not read either form: an exporter answers in text, and the Prometheus API returns lists. Two
new integrations read them:

- **Prometheus (PromQL query)** asks a server one expression for each value, for example
  `mem_active = node_memory_active_bytes{instance="192.168.0.1:9100"}`, and takes the first sample of the answer.
- **Prometheus exporter (/metrics scrape)** reads an exporter's page and takes the first sample that matches a
  metric name and optional `=` or `!=` label matchers, for example
  `root_free = node_filesystem_avail_bytes{mountpoint="/"}`.

Each instance reads up to 12 values, one line each, with a user name and password or a bearer token if the target
has a login. The values are the instance's metrics, so the **Alert on a metric** thresholds of every other
integration work on them, and an instance bound to a host (**Runs on host**) shows them on that host's card with
their trend. A query that returns nothing, a metric that is not on the page and a NaN make the instance a
warning that names them; nothing read, an unreachable server and a refused login make it critical. A line that
cannot be read is refused when you save, with its line number. Regular expression matchers are not supported on a
scrape; use the query form for those. See [integrations.md](integrations.md).

**Fields and thresholds come back.** The integration list did not send back a Custom HTTP probe's path, expected
status and JSON check, or the **Alert on a metric** thresholds of any integration, so the form showed them empty
and the next save from it removed them. They are sent back now, to administrators only, because a path can carry
a token.

## Security review

The release was reviewed against 7.4.2, the last reviewed release. It found four issues, and
all four are fixed:

- The Test buttons for integrations, mail, the directory, the ticket mailbox and Proxmox could
  be pressed by the administrator of any tenant, and each makes the server call an address or
  send mail that the request names. They belong to the platform operator now, like the saves
  beside them. Nothing changes on an install with tenancy off.
- The integration list showed a tenant administrator the raw address of every integration,
  a probe's path and a Prometheus instance's lines, and listed integrations bound to other
  tenants' hosts. With tenancy on it shows what a viewer sees and leaves those rows out.
- A host's report could make its own heartbeat fail with a 500: a number too large for a
  float, NaN, an infinity, a string or a list in the wrong place. Nine places read such
  figures safely now.
- The audit entry for a maintenance window says whether it holds notifications or raises no
  alerts.

The scans, the tests and what was left alone are written up in the 7.4.3 entry of the
[CHANGELOG](../CHANGELOG.md); the review itself has left the three kept.
