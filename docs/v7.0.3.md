# RemotePower v7.0.3 — "C4useMatters"

A release about failures that named the wrong cause.

A monitor said a host was down. The host was fine — a bot filter at the edge had
turned the probe away, and nothing in the failure said so. A TLS setting whose
own comment called it a floor was lowering one, so a server hardened to TLS 1.3
got handed a context that would still speak TLS 1.2. And a test helper written
to stop the Needs-Attention tests from interfering with each other could not see
six of the stores that digest reads, so it reported isolation it was not
providing.

Three different systems, one shape: the thing that told you what went wrong was
confidently wrong about it.

## A monitor reported a bot challenge as "host down"

A monitor aimed at a site behind Cloudflare failed continuously while the same
URL loaded fine in a browser and returned 200 to `curl`. Two independent causes,
both in how RemotePower makes an outbound request.

**It introduced itself as Python.** `urllib` sends `Python-urllib/3.x` unless you
say otherwise, and a Browser Integrity Check refuses that before the request
reaches the origin — so the origin's access log has nothing in it to explain the
failure. Both probe paths now send `RemotePower/<version>`, which every other
outbound call in the product already used.

**It put an older TLS version back on the wire.** The probe's SSL context
assigned a minimum of TLS 1.2. On a host whose OpenSSL configuration pins a
higher minimum, that assignment *lowered* it — and the extra version in the
handshake changed the client's TLS fingerprint enough for Bot Fight Mode to
challenge every probe.

`curl` returning 200 was not evidence the server was fine. It is a different TLS
client, so comparing it with the application compared two unknowns. The cause was
found instead by varying one component of the request at a time inside a single
process, which reproduced both directions six times out of six.

## A floor you set is not a floor you raise

The same assignment existed in ten more places, each with a comment calling
itself a floor: "refuse obsolete TLS 1.0/1.1", "pin the floor here". One of the
eleven guarded the value it was replacing. The other ten did not.

Eight are fixed: both server-side contexts, all three agents, the scanner
satellite's two contexts, the standalone scanner and the key server. Two of
those are listening sockets, where the setting decides which clients are allowed
in rather than which servers you will talk to.

Two are left as they were, each with its reason recorded next to it: an appliance
whose firmware negotiates TLS 1.0 and nothing newer, and a second appliance of
the same kind. Both are self-signed devices on a local network whose trust model
is the network plus an API credential, and both already sit beside a matching
security-level relaxation. Raising their floor would simply stop them working.

Turning off certificate checking for a self-signed box on your own LAN is not a
reason to lower the protocol version your operating system was configured to
require. Those are separate decisions and RemotePower now treats them that way.

## Isolation that was not isolating

The Needs-Attention digest reads about two dozen stores. Tests that exercise it
share a data directory with whatever else is running, so a helper repoints each
store into a private temporary directory first, and a guard fails if the digest
starts reading a store the helper does not cover.

The guard read the names inside the digest function and nothing else. Six stores
are reached through helpers it calls — configuration drift, the log buffer, and
four inputs to the reliability rollup — so those six stayed pointed at the shared
directory while the list read as complete. A neighbouring test leaving drift
state behind for a device id as ordinary as `d1` put a row in a digest that was
supposed to be empty.

The list has the six. The guard walks the call graph now, because a population
derived from one function body is what went stale — not the rule it enforced.

## Upgrading

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v7.0.3`).

No configuration changes are needed. If you run RemotePower on a host whose
OpenSSL configuration sets a minimum TLS version above 1.2, that setting is now
honoured rather than overwritten — which is the intended behaviour, but it does
mean a monitor aimed at a server that only speaks TLS 1.2 will start failing
where it previously succeeded. The monitor's error names the handshake as the
cause.
