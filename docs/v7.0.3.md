# RemotePower v7.0.3 — "C4useMatters"

A release about failures that named the wrong cause.

A monitor said a host was down. The host was fine — a bot filter at the edge had
turned the probe away, and nothing in the failure said so. A TLS setting whose
own comment called it a floor was lowering one, so a server hardened to TLS 1.3
got handed a context that would still speak TLS 1.2. And a test helper written
to stop the Needs-Attention tests from interfering with each other could not see
six of the stores that digest reads, so it reported isolation it was not
providing.

Three different systems, one shape: the thing that told you what went wrong was
confidently wrong about it.

## A monitor reported a bot challenge as "host down"

A monitor aimed at a site behind Cloudflare failed continuously while the same
URL loaded fine in a browser and returned 200 to `curl`. Two independent causes,
both in how RemotePower makes an outbound request.

**It introduced itself as Python.** `urllib` sends `Python-urllib/3.x` unless you
say otherwise, and a Browser Integrity Check refuses that before the request
reaches the origin — so the origin's access log has nothing in it to explain the
failure. Both probe paths now send `RemotePower/<version>`, which every other
outbound call in the product already used.

**It put an older TLS version back on the wire.** The probe's SSL context
assigned a minimum of TLS 1.2. On a host whose OpenSSL configuration pins a
higher minimum, that assignment *lowered* it — and the extra version in the
handshake changed the client's TLS fingerprint enough for Bot Fight Mode to
challenge every probe.

`curl` returning 200 was not evidence the server was fine. It is a different TLS
client, so comparing it with the application compared two unknowns. The cause was
found instead by varying one component of the request at a time inside a single
process, which reproduced both directions six times out of six.

## A floor you set is not a floor you raise

The same assignment existed in ten more places, each with a comment calling
itself a floor: "refuse obsolete TLS 1.0/1.1", "pin the floor here". One of the
eleven guarded the value it was replacing. The other ten did not.

Eight are fixed: both server-side contexts, all three agents, the scanner
satellite's two contexts, the standalone scanner and the key server. Two of
those are listening sockets, where the setting decides which clients are allowed
in rather than which servers you will talk to.

Two are left as they were, each with its reason recorded next to it: an appliance
whose firmware negotiates TLS 1.0 and nothing newer, and a second appliance of
the same kind. Both are self-signed devices on a local network whose trust model
is the network plus an API credential, and both already sit beside a matching
security-level relaxation. Raising their floor would simply stop them working.

Turning off certificate checking for a self-signed box on your own LAN is not a
reason to lower the protocol version your operating system was configured to
require. Those are separate decisions and RemotePower now treats them that way.

## Isolation that was not isolating

The Needs-Attention digest reads about two dozen stores. Tests that exercise it
share a data directory with whatever else is running, so a helper repoints each
store into a private temporary directory first, and a guard fails if the digest
starts reading a store the helper does not cover.

The guard read the names inside the digest function and nothing else. Six stores
are reached through helpers it calls — configuration drift, the log buffer, and
four inputs to the reliability rollup — so those six stayed pointed at the shared
directory while the list read as complete. A neighbouring test leaving drift
state behind for a device id as ordinary as `d1` put a row in a digest that was
supposed to be empty.

The list has the six. The guard walks the call graph now, because a population
derived from one function body is what went stale — not the rule it enforced.

## The rest of the release

The three above are the story the release is named for. A whole-project security
review ran alongside them, and a data-binding sweep asked, of every signal the
fleet produces, which screens actually show it. Both found more than expected.

### Security

Fourteen issues, all caught before release and all fixed here.
`docs/security-review-7.0.3.md` describes each one, what it would have taken to
exploit it, and what changed. The headline items: the web terminal connected with
SSH host-key checking off while sending your password, and the fingerprints
needed to verify the host had been collected with every heartbeat since v6.1.2
and consulted by nothing; three ways one tenant could reach another on installs
with tenancy enabled; two agent channels that ran commands as root while
read-only mode was on; and an API token that could be replayed across an HTTP
redirect.

### The API reference was returning 403 on every install

A rule in the shipped web-server configuration blocks requests for `.json` files,
so a data directory accidentally placed inside the web root is never served. In
nginx a regular-expression location outranks an ordinary prefix location, and the
API prefix is an ordinary one — so that rule, not the API, answered
`/api/openapi.json`, which is exactly what the API reference page fetches. In the
container image it also blocked the web-app manifest and every JSON asset under
`/static/`.

If you use the API reference page, it works again after this upgrade. Nothing to
change on your side.

### SAML metadata advertised an endpoint that does not exist

The metadata you hand your identity provider named an Assertion Consumer Service
URL that is not routed, so an assertion posted into a 404. If you set up single
sign-on by following the documentation and it never worked, this is why. Re-fetch
`/api/saml/metadata` and re-upload it to your provider, or change the ACS URL
there to `/api/auth/saml/acs`.

### Alerts say what they measured

The alert row shows the facts an alert stored, and thirty-one alerts stored none
of the ones that mattered. An ECC alert showed neither the correctable nor the
uncorrectable count, so "keep an eye on this" and "replace the DIMM now" looked
the same. A certificate expiry showed no days remaining. A break-glass credential
access recorded who took it nowhere. The predictive alerts — disk failure,
memory and CPU saturation — fired with the prediction removed.

Nothing to configure; alerts raised after the upgrade carry the detail.

### The printable report prints what you ticked

"SLA / uptime" and "Needs attention" were selectable in the custom report
builder, computed by the server, shipped in the JSON, and rendered nowhere in
the printed document. "Security posture" had no label at all, so its checkbox
showed a raw slug.

### Windows and macOS hosts answer three more questions

Firewall, disk encryption and automatic updates are reported by all three agents
under different names. The Checks page and the risk score have always read all
three. The Data Explorer, the Fleet Query facets and the printable report read
only the Linux one — so a Windows or macOS host answered "unknown" to "is this
disk encrypted", a query for hosts without a firewall silently excluded them,
and on a Windows-heavy fleet the report printed no posture section at all rather
than a wrong one.

### Signals you already collect, put to work

Four places that answer questions about your fleet were ignoring data the
agents already send.

**The Data Explorer can ask about five more things.** It could query devices,
CVEs and config drift. Installed packages, listening ports, watched services,
containers and the alerts inbox are queryable now, joinable and sortable like
the other three. A listening socket carries its exposure scope, so "who listens
on 3306 from the world" is one condition. A watched unit carries a `flapping`
flag, because a unit crash-looping under `Restart=always` reads `active` every
time it is sampled and no query on its state could find it. A package scan stops
at 100,000 rows and says when it did.

**The risk score reads five more signals:** UEFI Secure Boot switched off, a
canary file the agent could not place, files the integrity guard has
quarantined, failed systemd timers, and your own custom checks. Each weight is
tunable on Settings → Alert parameters, and 0 switches one off. Custom checks go
through the same evaluator as the Checks page, so the two cannot disagree.

**The compliance checklist takes four more sources as evidence:** OpenSCAP / USG
benchmark results, the privileged-command (sudo) trail, the regulated-data
inventory, and DMARC, SPF and DKIM posture. An empty result on a fleet that never
ran the scan reads **Not assessed**, never Pass.

**Prometheus exports ten more metric families** — swap, load, file-descriptor and
connection-tracking usage, failed units and mount issues, plus CPU count and
total memory and disk in base units — and the custom metrics you push from your
own hosts arrive as `remotepower_device_custom_metric`.

### The VNC console runs noVNC 1.7.0

The upgrade from 1.5.0 waited for a test that could watch the console work. That
test plays a real VNC server against the shipped viewer, from the handshake to a
rectangle painted on the canvas. It passed on 1.5.0 first, and passes unchanged
on 1.7.0.

### The Jellyfin connector works with Jellyfin 10.12

Jellyfin 10.12 stopped accepting the `X-Emby-Token` header by default, and that
was how the connector sent its API key, so every poll failed with
`HTTP 401 from /System/Info`. The key now goes in the `Authorization` header,
which older releases read as well. Your saved key keeps working.

### Translation

Thirty-seven more server-provided strings are translated into all six languages
— every ACME DNS credential field label and hint, which is the whole Settings →
DNS pane for eleven providers, plus the app catalog descriptions and the billing
rate-card labels. Two stay in English on purpose: an example URL and a list of
literal endpoint values, where a translation would be actively wrong.

## Upgrading

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v7.0.3`).

No configuration changes are needed. If you run RemotePower on a host whose
OpenSSL configuration sets a minimum TLS version above 1.2, that setting is now
honoured rather than overwritten — which is the intended behaviour, but it does
mean a monitor aimed at a server that only speaks TLS 1.2 will start failing
where it previously succeeded. The monitor's error names the handshake as the
cause.
