# RemotePower v6.4.1 — "Cust0dyMatters"

Key custody. RemotePower can now hold the encryption keys for the storage that
depends on it — a built-in **KMIP key server** so a Synology NAS, TrueNAS box or
vSphere cluster stops keeping its keys on the same hardware that holds the
encrypted data. It is off by default, runs as a separate sandboxed sidecar,
accepts mutual TLS only, and ships with an encrypted recovery bundle, because
key custody without a way back is a liability rather than a feature.

Alongside it: a cross-agent parity program that makes the Windows and macOS
agents honour what the server was already sending them (custom scripts, live
view, the PII scan, canary files, delta heartbeats, watched services, file-path
log rules), a dead-signal sweep that revived security signals collected but
never surfaced, the optional ingest receivers finally have an installer path,
the CLI shows what those receivers have actually ingested, and three defects
reported from the field are fixed — a monitor error message you can act on, one
stale monitor no longer blocking every other monitor edit, and a Settings
section that had quietly become four unrelated things.

After upgrading, hard-reload the dashboard once so the new front-end loads
(service-worker cache `remotepower-shell-v6.4.1`).

## KMIP key server

Storage appliances that encrypt data need somewhere to keep the keys, and
keeping them on the same box defeats the point. Synology DSM, TrueNAS and
VMware vSphere all speak **KMIP** to an external key manager — but the servers
that answer are enterprise HSM front-ends, so a homelab or small fleet has had
nowhere to point them. RemotePower now ships one, **off by default**.

`remotepower-kmipd` (tcp/5696, `install-server.sh --with-kmip`) is a native
KMIP 1.0–1.4 implementation over **mandatory mutual TLS**. It is deliberately
a protocol shim: it terminates TLS and parses TTLV, then forwards each
operation over loopback. It holds no keys, no master key and no data-directory
access — which is why its unit runs under `DynamicUser=yes`. Supported:
Discover Versions, Query, Create, Register, Get, Get Attributes, Get Attribute
List, Locate, Activate, Revoke, Destroy.

**Security → KMIP** is the whole surface: enable the server, then a three-step
wizard picks the appliance type from a dropdown, issues its certificate, hands
you `ca.crt` / `client.crt` / `client.key` (the private key shown once, never
stored), shows per-appliance setup steps, and waits for the client's first
connection so you can confirm it worked. Keys are AES-256-GCM at rest under a
dedicated master key, scoped to the owning client — one appliance can never
read another's. Every connection, authentication failure, KMIP operation and
admin action lands in an on-page **activity log**, which is as useful for
debugging a client that won't connect as it is for review.

**Recovery is first-class**, because key custody without it is a liability:
export a single passphrase-encrypted bundle holding the master key, CA, client
certificates and every key object — enough to rebuild the server on new
hardware. The master key is deliberately **excluded from scheduled backups**,
so a stolen archive holds only ciphertext. Restore refuses to overwrite a live
store without explicit confirmation.

One caveat the UI, installer and docs all state plainly: an appliance that
stores keys here needs this server reachable **at its own boot**. Never run it
on a machine that depends on it to unlock. See [kmip.md](kmip.md).

The whole subsystem was then hardened against a real first-run: certificates
appliances actually accept (SANs, key identifiers, a CA that validators treat
as a root), the attribute and lifecycle operations Synology DSM actually calls,
TLS handshake failures translated into what to fix ("the appliance does not
trust our CA — upload ca.crt into its trusted store"), a complete DSM
walkthrough in [kmip.md](kmip.md), a supported **Remove and start over**, and
an adversarial review that fixed two pre-release High findings in the listener
(a TTLV amplification and a pre-auth handshake stall) before anything shipped.

## Optional sidecars are installable, and visible in the CLI

`install-server.sh` gained `--with-kmip`, `--with-syslogd` and `--with-flowd`.
The syslog and flow receivers previously had no installer path at all — they
were documented as manual copy-paste. All three stay off by default: an install
should never open a port nobody asked for.

`rp status` and `rp tui` gained an **INGEST & KEYS** block that answers "is it
actually working?" rather than just "is it running?" — syslog sources mapped
and lines buffered, flow exporters reporting, KMIP client/key counts and recent
failures. It reads through the storage backend, so it stays correct under
Postgres and SQLite rather than silently reporting zero. `remotepower-kmipd` is
a first-class component row alongside the other sidecars.

## Monitors: an error you can act on

Two defects surfaced by a field report — *"adding a monitor fails, only for
http/https checks"*.

The **rejection message could not be acted on**. Every bad target produced
`Invalid monitor target: <url>`, which cannot distinguish a typo'd URL from a
perfectly good one that *this server's resolver* answers with a blocked
address. Only http/https and tcp resolve the hostname — ping, icmp and dns just
sanitize it — which is exactly why the failure looked type-specific and made no
sense. The message now names the resolved IP and the rule that rejected it,
and, for the common case, the setting that permits it:

> "bymanden.dk" resolves to 127.0.0.1 on this server, which is a loopback
> address. Monitoring it is blocked by the SSRF guard — enable Settings →
> "Allow monitoring of internal / loopback targets" if this is a service on the
> RemotePower host itself.

A filtering resolver answering `0.0.0.0` (Pi-hole, AdGuard) is called out by
name, as are link-local/metadata addresses, bad schemes and a tcp target with
no port. An unresolvable host is still *allowed* — "cannot classify" must not
become "reject", or you could never monitor something the server cannot
currently resolve.

**One stale monitor blocked every other monitor edit.** The editor re-posts the
whole list, so a single pre-existing entry that no longer validates — a
satellite since deleted, an older-schema tcp entry without a port, a target
whose DNS answer changed — rejected the entire save, naming the *other*
monitor. Adding, and even deleting, an unrelated monitor became impossible.
Now only the entry you actually touched hard-fails; an untouched broken one is
carried through verbatim and reported as a warning toast, so it cannot rot
unseen.

## Signals that were collected but never reached you

Four security signals and one hardware page were wired end to end in code and
dead in practice. Each passed review and passed the tests, because the tests
build the data the consumer expects and never ask whether anything produces it.

**CPU and board temperatures were missing from Thermal Health.** Disks and GPUs
appeared; `coretemp/Package id 0` never did. The agent collects the sensors and
the server stores them correctly — one level deeper in the record than SMART
and GPU data — and three readers looked at the shallow key. The same miss meant
the `overheating` risk and reliability signals could only ever fire on a hot
disk or GPU, never a cooking CPU. The Critical and Headroom columns were blank
for a separate reason: the sanitizer dropped the sensor's critical threshold.

**The Security Advisory's identity layer never produced a finding.** It reads
sshd's resolved configuration, which nothing collected. The agent now runs
`sshd -T` — the authoritative answer, since it resolves Includes and Match
blocks rather than reporting what the main config file happens to say — and
falls back to parsing the file, where a missing directive means the
compiled-in default rather than a clean bill of health. Root login, password
authentication, and permitted **empty passwords**, which is critical.

**TLS expiry** advice read a field that does not exist; it now uses the TLS
monitor's real results, and separates an expired certificate from an expiring
one. **Brute-force pressure** read the wrong store, and its advice now states
whether fail2ban is installed and jailing instead of asking you to check.
**An accepted-risk CVE** kept driving the advisory while disappearing from
Risk — the ignore list is applied now, along with **KEV** data, so a CVE known
to be exploited in the wild outranks a critical nobody has weaponised.

The advisory's `data` layer, declared since it shipped and empty ever since,
now carries secret-scanner findings, stale backups, FileVault and BitLocker.

## Risk scores what it already knew

`docs/risk.md` described CVEs weighted by KEV, container posture and backup
freshness. The scorer implemented none of the three — the doc described a
product that did not exist. Rather than trim the doc, the code now does what it
claimed, plus three more signals that were collected and scored nowhere. Each
is a tunable weight on Settings → Alert parameters, and 0 disables it:

- **CVEs on CISA's KEV list** rank above severity alone, because KEV means
  exploitation has been observed rather than predicted. A CVE you have accepted
  on the ignore list still does not count — accepting a finding keeps working.
- **Malware and AV posture** — an active detection, or real-time protection
  switched off. A host with no AV record at all is not a finding; absent data
  must not read as "infected".
- **CVEs in running container images**, at half the per-finding weight of a
  host package and capped, so one unpatched base image cannot swamp the score.
- **Stale backups, exposed credentials, and patch-SLA breaches.** The SLA
  breach set comes from the same evaluator the Patch SLA page uses, so the two
  can never disagree about whether a host is in breach.

The **Security Advisory** gains OpenSCAP results, which were a parallel scoring
silo with no route into "what should I fix" despite every failed rule carrying
a severity and a remediation id — and **agent-binary tampering**, which
previously reached nothing but a badge on the device row.

## One reading of each posture store

Risk and the Security Advisory stay separate — they answer different questions,
and a single artefact would answer one of them badly. But the layer below that,
how a store is actually read, was duplicated, and it had already caused a real
bug: Risk applied the CVE ignore list and the Advisory did not, so a CVE you
had accepted disappeared from one and kept nagging from the other.

`posture_signals.py` now holds that layer for CVE findings, stale backups,
secret findings, AV verdicts and container-image counts. It holds the
extraction and never the interpretation — points, severities and wording stay
with whichever system is interpreting, and a test fails if scoring vocabulary
turns up in it, because that would be the merge arriving by the back door.

Two more Advisory findings came out of it: **config files drifted from
baseline** (paths only — the captured diff can carry a credential, and the
Drift page already shows it) and **authorized SSH keys on deprecated
algorithms**. Two others were written and deleted: "ports opened since the
baseline" and "SSH keys added since the baseline". Both baselines are rewritten
on every heartbeat, so the delta is empty by the time the advisory reads it.
Those are events, they already alert, and a finding that cannot fire is worse
than no finding at all.

## macOS: custom checks and file-integrity watching were never running

The same shape as the dead signals above, on a different surface. The macOS
agent read 13 of the keys the server sends in its heartbeat response; the Linux
agent reads 48. Two of the gaps were features an operator could switch on from
the UI and get a success toast for.

**Custom checks assigned to a Mac reported `unknown` forever.** The server
pushed the check definitions, the UI showed them applied, and the agent never
read the list. It now evaluates them on every beat and reports results the same
way the Linux and Windows agents do. **Watched files produced no drift report
at all** for the same reason, and now hash on the sysinfo cadence.

A check type a Mac genuinely cannot evaluate — the Linux-only integrity and
egress guard types — reports `unknown` with the reason attached. That is a
deliberate third answer: reporting OK would be a silent false green, and
reporting critical would be an alert nobody can act on.

**New check type: `launchd_service`**, the macOS counterpart to
`systemd_unit` and `windows_service`, evaluated with `launchctl list`. A job
that is loaded but not running reports **warning** rather than critical,
because that is the normal state for an on-demand launchd job and treating it
as a failure would alert on healthy hosts. Ten macOS rows joined the check
catalog, and the check-type dropdown is now translated in all six languages.

The operator's `log_errors` regex is matched in Python against `log show`
output rather than being interpolated into the command, and a launchd label is
charset-validated before it reaches the argument list — the same posture as the
Windows agent's Event Log path.

## Cross-agent parity: the server was already sending it

The rest of the parity audit closed the configured-but-silent-on-this-platform
gaps across the Windows and macOS agents. Each of these was a feature an
operator could switch on from the UI, get a success toast for, and get nothing
from:

- **Custom monitoring scripts** run on both platforms. macOS ships `/bin/bash`,
  so it runs the body exactly as Linux does. Windows cannot, so the body
  declares its interpreter with a first-line `#!ps` or `#!cmd` marker — and a
  markerless Windows body is reported as a **failed run with an actionable
  message**, not silently skipped. Both honour observe-only audit mode.
- **Live view** works on both: the drawer's 1-second CPU/mem/disk/swap burst
  had only ever been read by the Linux agent, so the button armed live mode and
  the chart stayed empty. Needs `psutil` on the host; bounded so a bad deadline
  can never park the heartbeat.
- **The PII inventory scan** runs on Windows and macOS — a Windows file server
  is where regulated data most often actually lives. Same detection rules, same
  privacy contract (kind, count and line numbers, never the matched value);
  platform-appropriate default roots (user profiles, web roots and data drives,
  never system config).
- **Canary (honeytoken) files** are planted and watched on Windows and macOS —
  ransomware is overwhelmingly a Windows problem, so Linux-only was the wrong
  way round. The server also stopped silently dropping `C:\...` paths from the
  watch list. Checked on every heartbeat; the Windows uninstall removes the
  decoys it planted. (Caveat stated plainly: NTFS disables last-access times by
  default, so detecting a pure *read* is best-effort on Windows — modification
  and deletion, which is what ransomware does, are reliable everywhere.)
- **Delta heartbeats**: Windows and macOS agents now omit unchanged package /
  port / interface inventories like the Linux agent has since v6.2.2. On a
  representative Windows Server host a steady-state sysinfo beat drops from
  7,376 to 219 bytes — about 97% smaller.
- **Watched services on macOS** (`launchctl list` mapped onto the same
  active / failed / inactive vocabulary), so the Services page, failed-service
  alerting and flap detection cover Macs.
- **File-path log rules on Windows and macOS**, with the Linux state machine
  (rotation/truncation detection, first-sight bookmark, byte/line caps) behind
  platform-appropriate credential deny lists. And a fix that reached further
  than the port: `/api/logs` had been rejecting the synthetic `file:<path>`
  unit names with its strict systemd-name check — so file-path rules had been
  silently discarded at ingest **on Linux too**, since v3.0.1.
- **Disk-usage scans on macOS** (`du`, BSD flags, same bounds), so the
  "what to delete" drawer view works for a filling-up MacBook.
- The 202-busy `retry_after` hint is honoured by all three agents, and the
  Windows/macOS agent docstrings now carry an explicit list of the heartbeat
  keys that remain Linux-only.
- **The macOS agent log now rotates.** It had no logging configuration at all —
  launchd pointed stdout/stderr at a file nothing ever rotated, so it grew
  without limit. It now self-rotates (5 MB × 5, created `0640`) like the Linux
  and Windows agents.

## Self-update rings verify survival, not delivery

A staged agent-rollout ring counted a device as verified the moment the update
command left the queue — so with auto-promote on, a canary that died on the new
binary still "verified" and the broken update went fleet-wide: the exact
failure a canary ring exists to stop. A ring now verifies only when the device
heartbeats again **on the server's current agent version**; a consumed command
with no such heartbeat past a 10-minute grace counts as stalled, and a silent
canary halts the rollout.

## Smaller operator-facing fixes

- **Devices can be renamed.** The drawer's Settings tab gains a Name field —
  display-only, the reported hostname stays untouched, heartbeats never revert
  it, and a blank field never erases the name.
- **Firewall changes can be dry-run on the host before queueing.** For backends
  with a native check (`ufw --dry-run`, `nft -c`) the rule editor offers to run
  it through the run-and-wait exec path and folds the host's own verdict into
  the confirm dialog; iptables/firewalld keep the command-only preview.
- **Batch action confirmations name the hosts.** "Reboot 3 device(s)?" hid
  exactly the mistake a confirmation exists to catch — the dialog now lists the
  device names, with a danger-styled button for reboot/shutdown.
- **Backups stay in their own instance's directory.** The default backup path
  is now derived from the data directory rather than hardcoded, archives are
  built under a private name and published atomically (a `*.tar.gz` that exists
  is always complete), everything is created `0600`, and the pre-restore
  snapshot is encrypted under the same passphrase as the backups.
- The GeoIP Settings label now says where to get a free offline `.mmdb` and
  that the file is read locally with no egress.

## Translations

Eight passes over the surfaces the i18n gate does not scan — dropdown options,
form labels, table headers, doc cards, and a first measured pass over the
JS-rendered surface — added roughly 800 entries in all six languages, cutting
the untranslated static surface by more than half. Product names, protocol
tokens and column acronyms (SPF, TTL, SLA) deliberately stay in English, and
every translation is hand-written rather than templated, because a wrong
translation is worse than the English fallback.

## SNMP OID browser

The SNMP poll reads the OIDs RemotePower knows how to interpret. When a device
exposes something else — a vendor counter, a PDU's per-outlet draw, a UPS
runtime estimate — the device drawer's SNMP tab can now walk any subtree with
the device's stored credentials, from a preset or a typed OID. Well-known OIDs
are resolved to names; vendor-private ones stay numeric, because naming those
needs a MIB we do not ship and a confident wrong name is worse than a blank.
Admin-only, audited, capped per walk, read-only.

## Dialogs and dense controls

Dialogs no longer close when you click beside them on desktop, because losing a
half-filled form to a stray click is a real cost. Escape still closes, and
every dialog now has a **×** in its corner — injected centrally, so a new
dialog cannot ship without one. Touch and narrow viewports keep backdrop
dismissal, where the dialog fills the screen and a corner button is a smaller
target.

Widths were inconsistent enough that two dialogs opened from the same page
looked different sizes; there is now one scale, anchored on the CMDB dialog.
Bare toolbar selects, the alert-parameter number inputs, and the small buttons
and chips all got more room.

## Monitor history

The per-monitor check history held 50 entries — under an hour at the default
cadence, and the same window behind the Live Monitor sparkline, the latency
percentiles and SLO availability. It now holds 300 by default, tunable to 5000
on Settings → Alert parameters.

## Laptop signals on Windows and macOS

Three more signals from the same dead-signal sweep. `chassis`, `battery` and
`uptime_seconds` were collected by the Linux agent only — which left three
features dead on exactly the hosts they were built for.

Chassis-aware **offline grace** exists so a laptop that has closed its lid is
not treated like a server that has stopped answering; with no chassis field, a
closed Windows or Mac lid paged like a dead server. **Battery-health alerting**
and its hardware RAG line had nothing to read on the portable machines that are
the whole point of the feature. And the fleet **uptime leaderboard** filters on
`typeof uptime_seconds === 'number'`, so every non-Linux host was silently
missing from it — no error, just an incomplete board.

Both agents now collect all three under the Linux agent's exact field names and
record shapes (`ioreg`/`sysctl` on macOS, CIM on Windows, with `psutil`-free
fallbacks), so the sanitizer and every consumer light up with no server-side
change at all. Each degrades to an empty value off-platform rather than
raising: these run inside `try/except`, where an exception would be swallowed
and the field would simply never appear — which is the bug this whole sweep has
been about.

## KMIP on the Server-status page

The KMIP key server had a Checks-catalog row but not the informational
Server-status row its sibling sidecars have — so the one subsystem whose outage
stops encrypted volumes mounting was the one you could not see there. It now
follows the same contract as the syslog and flow receivers: reported only when
enabled, never a health input on its own. The row includes the soonest PKI
expiry across the CA and every live client certificate, because an expired
client certificate silently ends that appliance's key access.

It **alerts**, too. The agent's cert-file sweep covers certificates sitting on
a host; the KMIP CA and the per-client certificates this server issues have no
agent to report them, so they were the one expiry nothing watched — and the
consequence is sharper than a normal certificate lapse, because the failure
surfaces only when someone reboots a NAS. A new `kmip_cert_expiring` /
`kmip_cert_renewed` pair fires from a cheap six-hourly sweep (silent when KMIP
is off), edge-triggered on the set of expiring subjects and auto-resolving when
it empties. Revoked clients are ignored — they cannot fetch keys anyway, so
warning about them would be pure noise.

## A Settings section that had become four things

Reported: the **Listening-port & firewall audit** section had turned into a
grab-bag. Certificate-file expiry alerts, GeoIP database paths,
impossible-travel detection and warranty auto-lookup had each been appended to
it over time — which had the side effect of putting **Muted services** a long
way from the audit toggle it belongs to.

It is now four coherent sections — the audit and its mutes, Certificate file
expiry, Login geolocation, and Warranty auto-lookup — each with a pointer to
its documentation. Every one of the ten controls is kept and appears exactly
once, and the new section titles are translated in all six languages.

## `/api/health` is liveness-only

`GET /api/health` is unauthenticated by design, and it was returning the exact
server version. Nothing consumed it — every probe in the tree, from the Docker
`HEALTHCHECK` to nginx, only checks for a `200` — while an unauthenticated
caller could read the precise patch level and fingerprint instances against
version-specific advisories at scale. Liveness is the endpoint's whole job, so
that is now all it reports; authenticated callers read the version on the
Server-status page.

`/api/public-info` **deliberately keeps** its `server_version`. The
peer-instance connector reads it from a peer's no-auth endpoint to report that
peer's version, so removing it there would break federation. That endpoint is
the one intentional pre-auth version disclosure, not an accident — and it is
worth stating which of the two is which.

The demo seeder also gained KMIP, the NetFlow rollup and incident memory, which
were unseeded — so the pages the last two releases lead with rendered empty in
a demo instance. No key material or secrets are in the seed data.

## Drift no longer alerts on Snap doing its job

Snap puts the package revision in its unit filenames, so every `snap refresh`
looked like files appearing and disappearing under `/etc/systemd/system` — a
critical diff every few days on any Ubuntu host. Those patterns are excluded;
everything else in that directory is still compared byte-for-byte.
