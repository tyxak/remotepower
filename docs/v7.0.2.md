# RemotePower v7.0.2 — "Prec3dentMatters"

A release about the autonomy loop, prompted by a live instance where it had
refused every single thing it ever looked at.

The Autonomy page held 22 receipts. Fourteen said `no_precedent`, four
`no_verified_backup`, four `action_not_allowed`. Not one shadow verdict in weeks
of sweeps — which, for a feature whose whole adoption story is *run it in shadow
for a while and grade what it would have done*, means there was nothing to
grade.

Four separate causes. Three of them were gates that named a reason they did not
have, or never ran at all.

## Precedent could not accumulate

The loop acts only where your fleet has fixed the same thing before. It looks
in incident memory for prior incidents with the same signature, and needs two of
them with a 70% success rate.

It counted an incident as a prior fix only if the record carried a *recommended
action*. That field is filled from an AI triage verdict and from nothing else.
With no AI provider configured — the default, in a product whose point is that
it needs no paid external dependency — confidence came out at zero however many
incidents your fleet had resolved.

It was worse than neutral. An outcome a person confirmed counts double one
written by the advisor, on the reasoning that an engineer who was there is
better evidence than a model nobody contradicted. So a resolution note you wrote
counted double toward the denominator and nothing toward the numerator: **a
fleet whose incidents people fix scored lower than a fleet with no memory at
all.**

Two operator-resolved incidents with written notes produced a confidence of
0.000 and a `low_confidence` refusal. The same two rows with an AI recommendation
attached produced 1.000 and a verdict.

## Nothing recorded a fix that worked

Two sweeps already computed exactly that, and kept only the failure half.

Press **Fix** on an alert row and a sweep checks a few minutes later whether the
alert closed. If it did not, you get `mitigation_unverified`. If it did —
nothing happened. An automation rule's remediation was verified the same way,
marked verified in its ledger, and remembered nowhere.

Those are the strongest evidence there is: this exact signature, on this fleet,
closed by this exact command. Both are recorded now, and so are the loop's own
verified actions. Four things count as a prior fix, and only the last needs a
model:

- a fix an operator ran that cleared its alert
- an automation rule whose remediation verified
- one of the loop's own actions that a person approved and that came back
  verified against the host's own checks
- a resolution note you wrote when closing an alert, or an AI triage verdict

Each incident yields at most one record, whichever sweep sees it first. Two
outcomes from a single incident would satisfy "two prior incidents" on the
strength of one, which is not what the rule says.

### And you can decide not to wait for it

**Only act where this fleet has fixed the same thing before** is a checkbox on
the safety envelope. It is on by default. Unticking it accepts the curated
command catalog as the plan instead — the commands live in the source next to
the safety analysis, so this is not the loop improvising.

That is a real trade-off, which is why it is a switch you flip rather than
something that quietly happens. Before this release the alternative it offers
existed in the code, was described in the docs, and could not be reached.

## A backup is not what makes restarting networking safe

"Destructive" and "can lose data" were one flag. So `restart_networking` on an
unreachable-gateway alert refused with `no_verified_backup` — four times on the
fleet that prompted this release. A restore drill is not what makes restarting
NetworkManager safe or unsafe, and no amount of backup testing would ever have
let that action through. The refusal read as *go and fix your backups*, which is
advice about a different problem.

They are separate questions now:

| Needs a proven restore first | Does not |
|---|---|
| patch, reboot, remount a read-only filesystem, rotate a credential | terminate a process, restart networking, enable the firewall, shut down |

The second column is still destructive. Those actions still need to be on your
allow-list, still count against the blast-radius limit, and still escalate for a
second pair of eyes. What they no longer do is demand evidence about a risk they
do not carry.

## "Only inside a maintenance window" had never been evaluated

The check called a function that does not exist in the codebase, behind a guard
that skipped it when it was absent. The guard was always false, the answer was
always *yes, act*, and the ticked checkbox did nothing at all.

It now honours **change-gated** maintenance windows — the same ones that already
hold an operator's own commands until the window opens. Refusing is the right
answer here rather than holding: a queued command fires whenever the window next
opens, hours later, on a decision made against evidence that has moved on.

A plain maintenance window is not a change window. A plain one means *expect
noise from this host*; reading it as permission to act would have the loop
working precisely when nobody is watching the alerts. And a host that no
change-gated window covers is never held, so the default of *on* holds where you
asked for it and deadlocks nobody who never declared one.

## Two mappings aimed at the wrong thing

When an alert did not name the unit, container, process, mount point or storage
pool, the loop fell back to the alert's `name` field. Every alert in RemotePower
uses `name` for the **device**.

So an overdue scrub on `web01` built `zpool scrub web01`, and a read-only
filesystem built `mount -o remount,rw web01`. Both were reachable, and both
would have been recorded as an action taken.

The fallback is gone. An alert that does not say which thing broke refuses with
`missing_parameter`, which is what the receipt should have said all along. A
read-only filesystem reporting exactly one path is remounted; two or more
refuses rather than fixing one and leaving the rest broken while the receipt
claims a fix. The Windows Update service, which no alert names because there is
only one of it, is filled from a small table of constants in the source.

## Two more things it can do, and five it will no longer pretend to

| Action | Where | Triggered by |
|---|---|---|
| `enable_av_realtime` | Windows | real-time malware protection switched off |
| `enable_gatekeeper` | macOS | Gatekeeper switched off |

Twenty-five action classes now. Five were **removed**, four of them added
earlier in this same release cycle and one that shipped in v7.0.0 — because an
adversarial review of this work asked, of each one, whether the alert that
triggers it names a host and whether the command can fix the state that fired
it. Five could not answer both.

| Removed | Why |
|---|---|
| `restart_resolver` (v7.0.0) | `resolver_unhealthy` is a **server-side** DNS check over targets you configure. Its alert names no host, and the loop resolves a host before it does anything else. |
| `flush_dns_cache` | Added here, beside it, and inherited the same dead trigger before either had ever run. |
| `enable_autoupdates` | Walking every state the agent's collector can produce, there is essentially none where the alert fires *and* `systemctl enable --now` fixes it. On Debian the alert means the periodic switch in `20auto-upgrades` is off while the unit is already enabled — the command exits 0 having changed nothing. |
| `remount_all` | `mount -a` skips filesystems that are already mounted, which is exactly the *stalled* case the alert usually means. A guaranteed no-op that consumes the tenant's whole hourly budget. |
| `shutdown_host` | The product **already** shuts hosts down on a failing UPS, and that path is opt-in on two axes and shuts down the *dependents*. This one targeted the machine reporting the UPS — the NUT master — honoured neither axis, and by powering it off first would have ended the telemetry that protects everything else on that UPS. |

Three mappings went with them for the no-host reason: `wan_down` (whose own
source comment says "fleet singleton, no device_id"), `mailflow_delayed`, and
`server_disk_low` — which is the **controller's own** data directory, not a
fleet host, and had the whole six-rung disk ladder attached to it. That ladder
moved to `disk_predict_fail`, which is the per-host signal it was written for.

And `oom_detected` no longer maps to `kill_process`: the alert's process name is
the one the kernel *already* killed and systemd has since restarted, so the
action would terminate the fresh one — into the middle of crash recovery on a
database — and nothing resolves that event, so it would repeat every hour.

Some were considered and left out, which is worth recording so nobody
re-derives it: container image updates and stale VPN handshakes carry no device
at all; a missing service dependency names a host, not a unit; a stale snapshot
would need a command that branches on ZFS versus btrfs, which the command
grammar cannot express; and `systemctl reset-failed` would clear the alert
without fixing anything, which is the sort of fix this loop exists not to make.

## Receipts can be cleared

A **Clear receipts** button on the card, and a delete button on each row.

Both are admin-only and audited — who cleared it, how many rows, and how many of
those were still waiting on their verification sample, because deleting one of
those drops the second half of its measurement. On a multi-tenant install you
clear your own tenant's rows and nobody else's. Clearing changes nothing the
loop decided and does not stop it running.

## The page says what it means

The safety envelope's labels were describing the old behaviour. "Destructive
actions need a proven-recoverable backup" is now "Actions that can lose data",
with the list. "Only inside a maintenance window" is "Only inside a change
window", with the note that it holds nothing on a host no such window covers.
Each row in the allow-list shows `needs backup` separately from `destructive`,
because they are separate questions.

## Upgrading

Nothing to do. The new checkbox defaults to the behaviour you already had, the
new actions are all off until you tick them, and an existing policy that has
never heard of `require_precedent` reads as *on*, which is what it was doing
anyway.

If your Autonomy page is full of `no_precedent`, it will stay that way until
either two fixes have been recorded for a signature or you untick the box. That
is the honest answer: the loop now has a way to learn, and learning takes a
couple of incidents.
