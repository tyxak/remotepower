# RemotePower v8.0.2 — "C0verMatters"

A release that fills in what was missing from pages you already use. One enrolment token can enrol many hosts. Passwords can be remembered and can age,
and you choose how dates and the clock are written. A smart group can be previewed before you save it, the Patches page shows how long patching takes,
the Data Explorer lists hosts by their hardware, software metering can carry what a licence costs, and a notification destination that keeps failing is
marked in Settings. Windows and macOS hosts now send the software installed on them, so the software views stop leaving them blank.

## Security

With tenant isolation on, a tenant administrator could set the password of an account in another tenant, the platform operator's included, and could
download the export of every tenant: the hosts, the accounts with their password hashes, and the settings. Both belong to the platform operator now.
This is in 8.0.0 and in the 8.0.1 pre-release, and in 7.5.0, the oldest release it was checked in. We found it while testing the password history.
Before this release an administrator's password reset was not on the audit log, so the log cannot show whether it was used. If you have tenant
administrators you do not fully trust, change the platform operator's password after you update.

Three more fixes close ways to reach what you did not hand out:

- **The export you can share carried every account's credentials.** Its `users.json` held each account's password hash, two-factor secret and recovery
  codes. It holds none of them now. If you gave an export from 8.0.1 or an earlier release to anyone, treat the password hashes and two-factor secrets
  in it as exposed: have those people change their passwords and set up two-factor authentication again. The full backup still holds them, because it
  restores accounts, so keep it private and set `RP_BACKUP_PASSPHRASE`.
- **An API key with a host scope reached hosts outside it.** A key can be given part of the fleet, and that scope confines even an administrator's
  key. Three groups of routes checked the tenant and not the scope. A key limited to the web servers could list, approve (which queues the command on
  the host), reject and clear the pending confirmations of a database host, read, switch off and delete the inbound tokens pinned to it, and see the
  member count of every smart group in the tenant and, with `?members=1`, their ids. A host outside the key's scope is answered with a 404 now, as
  another tenant's host is, and nothing changes. A key with no scope behaves as before.
- **The install link is no longer written to the nginx access log.** The Quick install command puts the enrolment token in the link, and nginx printed
  the request line whole. A token for one host stops working once that host has enrolled, but one made for many hosts stays good until it is spent or
  expires, so the log would have held working tokens. See [After you upgrade](#after-you-upgrade) if you edited the nginx snippet.

## After you upgrade

- Hard-reload the dashboard once so the new front end loads.
- **Update the Windows and macOS agents.** They send the software installed on the host now, and until you update them those hosts stay blank in the
  software views. The Linux agent changes in its version number and in one message: after it enrols with a token it removes
  `/etc/remotepower/enroll-token` and now says why. Nothing else about it changed.
- **If you edited the nginx snippet that ships with RemotePower, add `access_log off;` to its `location = /install` and `location = /install.ps1`
  blocks.** An update copies the new file into place, which is enough if you did not edit it. A proxy of your own in front of the server logs the link
  unless you tell it not to: turn its log off for those two paths, or have it log the path without the query string.
- If you gave an export from 8.0.1 or an earlier release to anyone, read [Security](#security).
- No setting turns on by itself. The two password rules are off until you set them, a token enrols one host until you make it for more, and dates and
  the clock are written as before until a person chooses.
- The **Mean time to patch** card starts empty. History starts at the upgrade, and the card shows a number once five patches have completed.

## One install command for many hosts

A token enrolled exactly one host, which does not fit group policy, a golden image or an autoscaling group. In **Hosts → Enroll host**, set **Hosts
that can use it** (1 to 1000, default 1) before you choose **Quick install command** or **Generate Docker compose**. The **Guide me** wizard has the
same field. Through the API it is `max_uses` on `POST /api/enrollment-tokens`.

- Each host that enrols uses one. A host that enrols again uses one again. A host that is refused, because the fleet is at its host limit or a known
  host sent the wrong host token, does not.
- The token lasts until its uses are spent or it expires: 24 hours by default, 7 days at most. Nothing raises the number later, so make another token.
- **Enroll host** lists the commands that are still open as *used 2 of 10*, with the time they have left and a **Revoke** button. Revoking stops further
  use at once. The audit log has a line for each host that enrolled, with the host's id and the first characters of the token, never the token.
- The window opens at 1 host each time, so a number left from an earlier command cannot turn the next Docker file into a token for 400 hosts.

Anyone who holds the command can enrol that many hosts until it expires. Make it for the number you expect, give it a short life, and limit it to your
networks with `allowed_cidrs`. The server accepts 10 enrolment attempts a minute from one address, so hosts that start at once behind one NAT address
get a 429 after the tenth. The installer stops, and the refused hosts have not used a use, so run it again. A copy of the command also stays in the
shell history of each host: revoke it when the rollout is done. See [One command for many hosts](install.md#one-command-for-many-hosts).

## Remember passwords and set a maximum age

**Settings → Security → Password policy** has two new rules. Both are off until you set them, and only the platform operator can set them.

- **Passwords remembered** (0 to 24). A new password cannot be the one in use or any of the ones before it, N in all. At 3, a person changes P1 to P2,
  P3 and P4, and the fourth change, back to P1, is accepted.
- **Maximum password age** (0 to 3650 days). A local password older than the limit has to be changed when its owner next signs in, before anything
  else works. The only other thing that session can do is sign out, and that ends it on the server like any other sign-out. An account with no
  recorded change date starts its clock at its own first sign-in after you turn the age on, never all at once.

Both apply to local passwords. Accounts that sign in through LDAP, OIDC, SAML or a passkey are not aged, and an API key has no password. A script that
signs in with a user name and a password is aged like anyone else, so give it an API key. Turning the age off later does not lift a change an account
was already told to make.

Password changes, administrators' resets and changes refused because the password was used recently are on the audit log now, with the account's name
and never a password. Before, a reset left no line. The history keeps only hashes, it is in no answer and no log line, and the full backup holds it next
to the password hashes. Checking it costs one password check for each password kept, so a caller can ask ten times a minute and gets a 429 after that.
The offline `remotepower-passwd` tool sets a password without these checks.

A new password can be at most 72 bytes, which is bcrypt's limit: 72 letters or digits, or fewer characters if it uses accents or other scripts. A longer
one is refused with a message that says so. Before, it ended in an internal server error. The password tool and the installers hash a longer password
with PBKDF2, so a long `RP_ADMIN_PASS` in a Docker file no longer stops the container from starting. An account that must change its password can now
sign out: the request used to be refused and the session stayed alive on the server until its token expired. See [Authentication](security.md#authentication).

## Software on Windows and macOS hosts

Windows and macOS hosts were blank in the software search, the Software center, the software policy, software metering, the SBOM and the CVE page. Their
agents send the installed software now.

- **Windows.** The agent reads the programs of Programs and Features from the Uninstall keys of the registry, the 64-bit one and its 32-bit twin. It only
  reads: it never loads, saves or writes a registry hive.
- **macOS.** The agent reads the applications in `/Applications`, `/System/Applications` and each account's `Applications` folder, and the Homebrew
  formulae and casks. It never follows a symlink out of an application folder, and it runs Homebrew as the account that owns it, never as root.

They send the list when they start, about every six hours and when you ask: **Scan packages** in a host's quick actions, **Scan now** in its Packages
section, or **Send list** on the CVE page. A list that has not changed is not sent again. A host keeps at most 5,000 rows.

**Not listed:** updates and hotfixes, components Windows hides from its list, a program installed for one user alone, an app from the Microsoft Store, a
portable program, and a Mac application kept outside the folders above. The agents count what they leave out, and the SBOM says how many.

How the views read such a list:

- Names match without regard to case, so a rule or a search for `teamviewer` finds `TeamViewer`.
- A version is read by the number it starts with, and the words after it come second. `14.38` is above `14.9`, and `2.43.0.windows.1` is above `2.9`
  and below `2.100`. A version with no number in front sorts below every version that has one.
- A **required** rule with no tags is checked on Linux hosts only, because it was written for the packages of a distribution and every Windows host
  would otherwise break `auditd`. **Banned** and **min_version** rules apply to every host that has a list. The **Fix** button is not offered for a
  Windows or macOS host.
- Metering counts applications and never calls one reclaimable: a title such as `Google Chrome` is not the name of its process.
- **No vulnerability database is matched against applications.** Their titles are not names any advisory is filed under, and a scan under a wrong name
  would read as clean. The CVE page says **not checked** for these hosts, and the host view says that nothing on it is checked.
- Install, uninstall and hold are Linux commands and skip these hosts. A request that queues nothing at all is refused with a 400 that says why, where
  it used to answer "queued on 0 hosts" in the colour of a success.

See [Software inventory](patches.md#software-inventory) and [Windows and macOS hosts](cve.md#windows-and-macos-hosts).

## How long patching takes

The Patches page has a **Mean time to patch** card. A patch is timed from the first hourly check that saw an update waiting on a host to the first check
that saw none waiting. The card shows the mean, the median and the 90th percentile, with the number of completed patches behind them, over the last 30
or 90 days, for all updates and, on a line of its own, for security updates.

- With fewer than five completed patches the card says so and shows no number. A host with none is left out and never shown as zero.
- **History starts at the upgrade.** An update that was already waiting when you upgraded starts its clock at the upgrade, and a time is accurate to
  about an hour.
- It needs no Patch SLA rule. The hourly sweep that does the timing runs on every installation now.
- The same figures are in the `mttp` field of `GET /api/patch-report`, for the fleet, for each host and, for the operator of an installation with tenants,
  for each tenant.

See [Mean time to patch](patches.md#mean-time-to-patch).

## Hosts by hardware in the Data Explorer

A new **hardware** entity has one row for each host you can see, with 24 fields from what the agents already report: maker, model and serial number, chassis,
CPU model and count, memory modules, disks, RAID arrays and graphics cards, and when the hardware was last stored. Ask for hosts by CPU model, by make and
model, or with a disk of a given model, in a query, a batch or a saved query.

A host that has not reported its hardware is a row of empty cells. The serial number is shown to the people who see it on the host's Hardware tab. **There
is no BIOS version**, because no agent reports one, so "BIOS older than X" cannot be asked yet.

Digits typed alone in a condition now find hosts. The page used to turn them into a number, so `7302` found nothing in a processor model although
"EPYC 7302" did. It sends the text as typed, and the server reads the value against the field. See [the hardware entity](data-explorer.md#hardware).

## What a licence costs

A software metering rule can carry the cost of one licence: `nginx = 10 @ 49.99`. The limit is the number of licences you own. With a cost the table adds
**Owned**, **Unit cost**, **Short by**, **Cost to buy**, **Spare** and **Cost to reclaim**, with a fleet total under it, in the currency of your billing
settings. The CSV carries the same columns.

A cost is an amount from 0 to 1,000,000 with at most two decimals. Anything else is refused and nothing is saved. A rule with no cost shows no amount, not
0.00. Only an administrator and the finance role of your own organisation see the money; everyone else sees the counts and no price. See
[Licence cost](reports.md#licence-cost).

## Smaller changes

- **Date order and clock.** **My Account → Profile → Language** has **Date order** (Automatic, day first, month first or year first) and **Clock**
  (Automatic, 24-hour or 12-hour). They are saved to your account, so they follow you to other browsers, and **Automatic** writes what the page wrote
  before. Day first reads 7/11/2026 in English and 7.11.2026 in German, and year first is always 2026-11-07. E-mails, exports, the public status page,
  the customer portal, the printable report and the fleet query page keep their own formats. See [My Account](my-account.md).
- **Preview members.** The smart-group editor has a button that shows how many hosts the rules match, and the first 50, before you save. The count comes
  from the same check the saved group uses. You see only your own tenant's hosts, and a key with a host scope only the hosts of its scope. A preview
  stores nothing. See [Groups](sites.md#the-groups-tab).
- **A failing destination is marked.** After three failed deliveries in a row the card of a destination in **Settings → Notifications** shows a red
  **Failing** mark, how many deliveries failed in a row and the kind of the last error, never the address. Only the administrator sees it. It goes when a
  delivery gets through, and when you change the destination's address, format or credentials. See
  [A destination that keeps failing](webhooks.md#a-destination-that-keeps-failing).
- **Keyboard focus rings are no longer cut off** in four scrolling lists: the AI Insights cards, a Knowledge base article, the Links page and a CMDB
  asset's documents. Focus also returns to a button whose handler disabled it, so a screen reader keeps its place.
- **A refused export is not saved as a file.** A tenant administrator who pressed **Export** used to be saved a `backup.zip` that held the error, under
  a green message. Nothing is saved now, the page says **Export failed**, and the **Backup & restore** card is drawn for the platform operator only.
- The time of a request sample on the Threat Intel page is exact when you hover it.

## Fixed on the way

- **A settings document applied back put `(redacted)` over the credentials of your destinations.** With a config master key set, applying an export
  unchanged replaced each destination's secret with that text, because destinations had no id to be matched by. They are matched by id now, and the
  preview of an import lists a destination as changed only when a field differs.
- **A failed read of the host store no longer empties what the sweeps keep for each host.** The health history, the metric and thermal roll-ups, the
  dependency edges and the Patch SLA aging took an unreadable host store for an installation with no hosts and dropped what they held. They keep it now
  and try again at the next pass.
- **Two stores that hosts write are written under their lock.** The software policy's violations and the brute-force detector's window lost entries when
  hosts sent together, which made `software_policy_violation` fire again for a host that had not changed, and made a brute-force alert late or lost.
- **Deleting a host clears the addresses its sensor queued** for Threat Intel.

## What was not tested

- **The Windows and macOS agents did not run on a real Windows or macOS host.** They were tested with a stand-in for the registry, application bundles
  written to a temporary folder and a script in place of Homebrew. Whether every application that ships with macOS, Safari included, is listed is not
  confirmed.
- The date and clock choices were run in Chromium and in Node's engine. Firefox and Safari take month names and 12-hour spacing from their own engines.
- The recording behind Mean time to patch was tested by calling the sweep at chosen times, not over a week of real sweeps.
- There is no nginx on the machine this was built on, so `access_log off` was checked as text and against a model of nginx's rules, not on a running server.
- The stores this release added or changed (the tokens' use counts, the password history, the completed patches, the software lists of Windows and macOS hosts, the
  failing-destination streaks) are in the storage registry, so the JSON, SQLite and Postgres backends all carry them. The tests ran them on JSON and SQLite; Postgres was not run.
