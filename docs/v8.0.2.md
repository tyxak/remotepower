# RemotePower v8.0.2 — "C0verMatters"

A release that fills in what was missing from pages you already use. One enrolment token can enrol many hosts. Passwords can be remembered and can
age, and you choose how dates and the clock are written. A smart group can be previewed before you save it, the Patches page shows how long patching
takes, the Data Explorer lists hosts by their hardware, software metering can carry what a licence costs, and a notification destination that keeps
failing is marked in Settings. Windows and macOS hosts now send the software installed on them, so the software views stop leaving them blank. Windows
hosts also report their build, file shares and TPM, can be checked for one registry value, matched in the event log and watched for what starts by
itself. A Linux host can refresh its package lists on request, and its drawer says what its agent can see. A CVE scan says which packages it checked
and why not the others, and matches the findings of the kernel against the kernel the host runs.

## Security

With tenant isolation on, a tenant administrator could set the password of an account in another tenant, the platform operator's included, and could
download the export of every tenant: the hosts, the accounts with their password hashes, and the settings. Both belong to the platform operator now.
This is in 8.0.0 and in the 8.0.1 pre-release, and in 7.5.0, the oldest release it was checked in. We found it while testing the password history.
Before this release an administrator's password reset was not on the audit log, so the log cannot show whether it was used. If you have tenant
administrators you do not fully trust, change the platform operator's password after you update.

Three more fixes close ways to reach what you did not hand out:

- **The export you can share carried every account's credentials.** Its `users.json` held each account's password hash, two-factor secret and recovery
  codes. It holds none of them now. If you gave an export from 8.0.1 or an earlier release to anyone, treat the password hashes and two-factor secrets
  in it as exposed: have those people change their passwords and set up two-factor authentication again. The full backup still holds them, because it
  restores accounts, so keep it private and set `RP_BACKUP_PASSPHRASE`.
- **An API key with a host scope reached hosts outside it.** A key can be given part of the fleet, and that scope confines even an administrator's
  key. Three groups of routes checked the tenant and not the scope. A key limited to the web servers could list, approve (which queues the command on
  the host), reject and clear the pending confirmations of a database host, read, switch off and delete the inbound tokens pinned to it, and see the
  member count of every smart group in the tenant and, with `?members=1`, their ids. A host outside the key's scope is answered with a 404 now, as
  another tenant's host is, and nothing changes. A key with no scope behaves as before.
- **The install link is no longer written to the nginx access log.** The Quick install command puts the enrolment token in the link, and nginx printed
  the request line whole. A token for one host stops working once that host has enrolled, but one made for many hosts stays good until it is spent or
  expires, so the log would have held working tokens. See [After you upgrade](#after-you-upgrade) if you edited the nginx snippet.

A review of the whole release, run against 8.0.0 as well, found more of the same kinds. Every one of them is in 8.0.0 unless the entry says it is new in this release,
and each is closed:

- **A key could do what a person signs in again for.** Setting another account's password, switching SCIM on, turning single sign-on or LDAP on and changing what
  they trust ask for a fresh sign-in now. A key cannot give one, so they answer 403 to a key and prompt a person. A script that did any of these with a key must be
  run by hand.
- **A key with a host scope could lift it.** It could make an unscoped administrator key, make roles and accounts outside its scope, start auto-patch policies,
  rollouts, rules and maintenance windows on any host, and on the Threat Intel page clear the whole table and read every host's Request log. It stays inside its
  scope now.
- **The export carried more than accounts.** The SSH, SNMP, RouterOS and OPNsense logins of agentless hosts, tokens, a pre-shared key and the audit-chain keys were in it.
  Every store is masked now and three stores are left out. If you gave an export to anyone, treat what was in it as exposed.
- **`RP_CONFIG_KEY` covered one field of seven, and not the history.** Addresses and header values were in plain text, and each of the last ten settings versions held the
  whole document unsealed. All of it is sealed now. A settings document from another installation cannot be opened here, and its import says so.
- **A revoked session could come back, and queues lost writes.** Sessions, the command queue, the settings and the backup state are saved inside their locks.
- **Threat Intel could be fooled and could leak.** A request could name the address the sensor reports, a page of another site could get a visitor reported,
  sign-ins by passkey, SAML and OIDC did not protect their address, and with tenants a tenant read other tenants' evidence, the operator's settings and which
  addresses are protected. Update the Linux agent for the sensor fixes.
- **The vulnerability pages crossed tenants and could be made expensive.** Accepted risks, scans, totals and campaigns belong to one organisation, and a scan, an SBOM
  and a software policy cost what the fleet justifies and not what one host's list asks for.
- **A deleted host left data behind, and a host could fill the disk.** Four more stores go with a deleted host, an infrastructure-as-code answer is kept only if you asked for it,
  and a few more wrong-typed values are repaired on read.

The review is in [security-review-8.0.2.md](security-review-8.0.2.md).

## After you upgrade

- Hard-reload the dashboard once so the new front end loads.
- **Update the agents you want the new things from.** Each one changed in a different way.
  - **Windows agent.** It sends the software installed on the host and everything under [Windows hosts](#windows-hosts): the definition updates and
    the state of each Windows Update search, the build, the file shares and the TPM, registry checks, event log rules and the persistence inventory.
    Persistence and event log rules do nothing until a Windows agent of this version reports or reads: the **Persistence** section stays hidden for a
    host whose agent is older, and a log rule on an event unit reads nothing from it.
  - **Linux agent.** It refreshes the package lists when you press **Check for updates now** (an older agent is refused with a message and nothing is
    queued), reports what it can see, and reports the kernel it runs. A Linux host whose agent is older shows "This agent has not reported what it can
    see" in that section, and its kernel findings are matched against every installed kernel as before. It also says why it removes
    `/etc/remotepower/enroll-token` after it enrols with a token.
  - **macOS agent.** It sends the software installed on the host, as before. Nothing in it changed since then that you can see: the source gained a
    comment and one more name in the list of heartbeat keys it ignores.
- **If you edited the nginx snippet that ships with RemotePower, add `access_log off;` to its `location = /install` and `location = /install.ps1`
  blocks.** An update copies the new file into place, which is enough if you did not edit it. A proxy of your own in front of the server logs the link
  unless you tell it not to: turn its log off for those two paths, or have it log the path without the query string.
- If you gave an export from 8.0.1 or an earlier release to anyone, read [Security](#security). If you set `RP_CONFIG_KEY`, the settings versions kept from before are sealed the next time a version is saved.
- **Run Scan all hosts once on the CVE page.** An upgrade starts no scan. A host scanned before 8.0.2 states nothing about which of its packages were
  checked until it is scanned again, and the line under the tiles says how many such hosts it does not count yet. The kernel a host runs needs the
  8.0.2 Linux agent as well.
- No setting turns on by itself. The two password rules are off until you set them, a token enrols one host until you make it for more, the package
  list refresh before a scheduled scan is off until you turn it on, and dates and the clock are written as before until a person chooses. The two
  options that count and alert only on what can be fixed now say "an update or a reboot": they keep their value, and a finding that only needs a
  reboot counts and alerts like one an update clears.
- The **Mean time to patch** card starts empty. History starts at the upgrade, and the card shows a number once five patches have completed.

## One install command for many hosts

A token enrolled exactly one host, which does not fit group policy, a golden image or an autoscaling group. In **Hosts → Enroll host**, set **Hosts
that can use it** (1 to 1000, default 1) before you choose **Quick install command** or **Generate Docker compose**. The **Guide me** wizard has the
same field. Through the API it is `max_uses` on `POST /api/enrollment-tokens`.

- Each host that enrols uses one. A host that enrols again uses one again. A host that is refused, because the fleet is at its host limit or a known
  host sent the wrong host token, does not.
- The token lasts until its uses are spent or it expires: 24 hours by default, 7 days at most. Nothing raises the number later, so make another token.
- **Enroll host** lists the commands that are still open as *used 2 of 10*, with the time they have left and a **Revoke** button. Revoking stops further
  use at once. The audit log has a line for each host that enrolled, with the host's id and the first characters of the token, never the token.
- The window opens at 1 host each time, so a number left from an earlier command cannot turn the next Docker file into a token for 400 hosts.

Anyone who holds the command can enrol that many hosts until it expires. Make it for the number you expect, give it a short life, and limit it to your
networks with `allowed_cidrs`. The server accepts 10 enrolment attempts a minute from one address, so hosts that start at once behind one NAT address
get a 429 after the tenth. The installer stops, and the refused hosts have not used a use, so run it again. A copy of the command also stays in the
shell history of each host: revoke it when the rollout is done. See [One command for many hosts](install.md#one-command-for-many-hosts).

## Remember passwords and set a maximum age

**Settings → Security → Password policy** has two new rules. Both are off until you set them, and only the platform operator can set them.

- **Passwords remembered** (0 to 24). A new password cannot be the one in use or any of the ones before it, N in all. At 3, a person changes P1 to P2,
  P3 and P4, and the fourth change, back to P1, is accepted.
- **Maximum password age** (0 to 3650 days). A local password older than the limit has to be changed when its owner next signs in, before anything
  else works. The only other thing that session can do is sign out, and that ends it on the server like any other sign-out. An account with no
  recorded change date starts its clock at its own first sign-in after you turn the age on, never all at once.

Both apply to local passwords. Accounts that sign in through LDAP, OIDC, SAML or a passkey are not aged, and an API key has no password. A script that
signs in with a user name and a password is aged like anyone else, so give it an API key. Turning the age off later does not lift a change an account
was already told to make.

Password changes, administrators' resets and changes refused because the password was used recently are on the audit log now, with the account's name
and never a password. Before, a reset left no line. The history keeps only hashes, it is in no answer and no log line, and the full backup holds it next
to the password hashes. Checking it costs one password check for each password kept, so a caller can ask ten times a minute and gets a 429 after that.
The offline `remotepower-passwd` tool sets a password without these checks.

A new password can be at most 72 bytes, which is bcrypt's limit: 72 letters or digits, or fewer characters if it uses accents or other scripts. A longer
one is refused with a message that says so. Before, it ended in an internal server error. The password tool and the installers hash a longer password
with PBKDF2, so a long `RP_ADMIN_PASS` in a Docker file no longer stops the container from starting. An account that must change its password can now
sign out: the request used to be refused and the session stayed alive on the server until its token expired. See [Authentication](security.md#authentication).

## Software on Windows and macOS hosts

Windows and macOS hosts were blank in the software search, the Software center, the software policy, software metering, the SBOM and the CVE page. Their
agents send the installed software now.

- **Windows.** The agent reads the programs of Programs and Features from the Uninstall keys of the registry, the 64-bit one and its 32-bit twin. It only
  reads: it never loads, saves or writes a registry hive.
- **macOS.** The agent reads the applications in `/Applications`, `/System/Applications` and each account's `Applications` folder, and the Homebrew
  formulae and casks. It never follows a symlink out of an application folder, and it runs Homebrew as the account that owns it, never as root.

They send the list when they start, about every six hours and when you ask: **Scan packages** in a host's quick actions, **Scan now** in its Packages
section, or **Send list** on the CVE page. A list that has not changed is not sent again. A host keeps at most 5,000 rows.

**Not listed:** updates and hotfixes, components Windows hides from its list, a program installed for one user alone, an app from the Microsoft Store, a
portable program, and a Mac application kept outside the folders above. The agents count what they leave out, and the SBOM says how many.

How the views read such a list:

- Names match without regard to case, so a rule or a search for `teamviewer` finds `TeamViewer`.
- A version is read by the number it starts with, and the words after it come second. `14.38` is above `14.9`, and `2.43.0.windows.1` is above `2.9`
  and below `2.100`. A version with no number in front sorts below every version that has one.
- A **required** rule with no tags is checked on Linux hosts only, because it was written for the packages of a distribution and every Windows host
  would otherwise break `auditd`. **Banned** and **min_version** rules apply to every host that has a list. The **Fix** button is not offered for a
  Windows or macOS host.
- Metering counts applications and never calls one reclaimable: a title such as `Google Chrome` is not the name of its process.
- **No vulnerability database is matched against applications.** Their titles are not names any advisory is filed under, and a scan under a wrong name
  would read as clean. The CVE page says **not checked** for these hosts, and the host view says that nothing on it is checked.
- Install, uninstall and hold are Linux commands and skip these hosts. A request that queues nothing at all is refused with a 400 that says why, where
  it used to answer "queued on 0 hosts" in the colour of a success.

See [Software inventory](patches.md#software-inventory) and [Windows and macOS hosts](cve.md#windows-and-macos-hosts).

## How long patching takes

The Patches page has a **Mean time to patch** card. A patch is timed from the first hourly check that saw an update waiting on a host to the first check
that saw none waiting. The card shows the mean, the median and the 90th percentile, with the number of completed patches behind them, over the last 30
or 90 days, for all updates and, on a line of its own, for security updates.

- With fewer than five completed patches the card says so and shows no number. A host with none is left out and never shown as zero.
- **History starts at the upgrade.** An update that was already waiting when you upgraded starts its clock at the upgrade, and a time is accurate to
  about an hour.
- It needs no Patch SLA rule. The hourly sweep that does the timing runs on every installation now.
- The same figures are in the `mttp` field of `GET /api/patch-report`, for the fleet, for each host and, for the operator of an installation with tenants,
  for each tenant.

See [Mean time to patch](patches.md#mean-time-to-patch).

## Hosts by hardware in the Data Explorer

A new **hardware** entity has one row for each host you can see, with 24 fields from what the agents already report: maker, model and serial number, chassis,
CPU model and count, memory modules, disks, RAID arrays and graphics cards, and when the hardware was last stored. Ask for hosts by CPU model, by make and
model, or with a disk of a given model, in a query, a batch or a saved query.

A host that has not reported its hardware is a row of empty cells. The serial number is shown to the people who see it on the host's Hardware tab. **There
is no BIOS version**, because no agent reports one, so "BIOS older than X" cannot be asked yet.

Digits typed alone in a condition now find hosts. The page used to turn them into a number, so `7302` found nothing in a processor model although
"EPYC 7302" did. It sends the text as typed, and the server reads the value against the field. See [the hardware entity](data-explorer.md#hardware).

## What a licence costs

A software metering rule can carry the cost of one licence: `nginx = 10 @ 49.99`. The limit is the number of licences you own. With a cost the table adds
**Owned**, **Unit cost**, **Short by**, **Cost to buy**, **Spare** and **Cost to reclaim**, with a fleet total under it, in the currency of your billing
settings. The CSV carries the same columns.

A cost is an amount from 0 to 1,000,000 with at most two decimals. Anything else is refused and nothing is saved. A rule with no cost shows no amount, not
0.00. Only an administrator and the finance role of your own organisation see the money; everyone else sees the counts and no price. See
[Licence cost](reports.md#licence-cost).

## Windows hosts

These need the Windows agent from 8.0.2. Nothing below ran on a real Windows host: see [What was not tested](#what-was-not-tested).

### Windows Update: definition updates and the state of each search

Windows offers a Defender definition update several times a day. It used to count as a pending update, so every Windows host showed one or two at all
times, over the patch alert threshold, in the patch SLA and in the risk score. The agent reports them apart now. The pending count, the patch alert,
the patch SLA and the risk score leave them out, and the host's **Packages** card shows how many there were under **Definition updates**. The Defender
platform update and the definition updates of other products are still counted.

Each search says when it ran, whether it worked and where it asked: Windows Update, or a WSUS server that a policy points the host at. A search that
failed says why in one word (`timeout`, `access`, `service`, `network` or `unknown`) and never sends the text of an error.

A failed search keeps the count the host had, and the **Packages** card and the patch report say when that count was taken (*Last search failed
(access); count taken 5d ago*). For 3 days the reports use that count. After that it is too old to call the host patched: the patch reports list the
host as **No data** and keep the count and its date beside it. The Checks page has a row, **Windows Update search**, that turns amber after 3 days
without a search that worked and red after 14. See [Windows Update](windows-client.md#windows-update).

### Build, file shares and TPM

The agent reads the build number, the revision, the display version, the edition, the product name and the installation type from the registry. The
**OS** row of the host's System info and the Hosts list show *Windows 11 Pro 23H2 (build 22631.3593)*. The family comes from the build number (22000
and up is Windows 11), because many Windows 11 hosts still write "Windows 10" into the product name. The Data Explorer has `win_build`, `win_ubr`,
`win_display_version`, `win_edition`, `win_product` and `win_family`, and Fleet Query has **Windows build contains**, so "which hosts are still on
Windows 10" is a query. Use `win_family` for it, not `win_product`. See [Windows version and build](windows-client.md#windows-version-and-build).

The agent also asks for the file shares the host exports and for its TPM. The administrative shares (`ADMIN$`, `C$`, `IPC$` and any name that ends in
`$`) are counted and not listed, and at most 100 others are listed. A probe that cannot answer sends nothing, and a host that never reported is not
read as a host without a TPM or without shares. System info has a **Shares** row and a **TPM** row. The Data Explorer has `shares_count`,
`tpm_present` and `tpm_ready`, and Fleet Query has **Shares >** and **TPM**. No alert and no check reads either. See
[File shares and the TPM](windows-client.md#file-shares-and-the-tpm).

### A registry value as a check

In the **Add check** dialog choose the type **Windows registry value**, then give a path under `HKLM\SOFTWARE` or `HKLM\SYSTEM`, a value name and a
condition: equals, does not equal, is at least, is at most, is set or is not set. The Windows agent reads that one value and reports it like any other
check, so alerts, mutes and the Checks page work as before. A Linux or macOS host in the same scope is not given the check and shows no row.

- **It only reads.** The agent opens the key for reading, in the 64-bit view, and never writes. It refuses another hive (it runs as SYSTEM, so `HKCU`
  would be its own), a path outside `SOFTWARE` and `SYSTEM`, a path of more than 12 parts, and a character that is not a letter, a digit, a space, a
  backslash or one of `. - _ ( ) { }`. The server checks a definition when you save it, and the agent checks it again.
- **What comes back** is a number or a text of at most 200 characters. A binary value is reported as `binary, N bytes`.
- **A secret stays off the page, as far as the agent can tell.** A text value whose name looks like a password or a key is not read at all, and in any
  other text the password after a name such as `password`, `token` or `secret`, and the password of a URL, are replaced. That is a second line of
  defence, not a guarantee: a secret written with no such name before it is not found, so do not point a check at a value that holds one.
- **A value that is not set** passes *is not set* and *does not equal*, and fails the other conditions.

Six ready-made checks are in the **Hardening — Windows registry** group of the Protect picker: SMBv1 server off, NTLM level 5, UAC enabled, Defender
real-time protection not disabled by policy, RDP network-level authentication required, and cached logons at most 4. See
[Windows registry values](checks.md#windows-registry-values).

### Event log rules

A log rule on a unit such as `eventlog.Security.4625` matches that event id in the Security, System or Application log of a Windows host. The agent
reads only the events that the rules of its host name, with `wevtutil`, and sends each event id as a unit of its own. From there it is an ordinary log
rule: the same pattern, threshold, severity and message, the `log_alert` alert and the same mutes. A line is built from the fields of the event, not
from its message, which is in the language of the host.

**Ready-made Windows rule** in the **Add rule** dialog fills in one of eight: failed logons (4625, ten or more in one report), account lockout (4740),
a service installed (7045 in System, 4697 in Security), a scheduled task created (4698), a local user created (4720), a member added to Administrators
(4732) and the audit log cleared (1102). Each note says which audit policy the event needs: 4697 and 4698 are logged only when theirs is on.

- **Nothing repeats and nothing is skipped.** The agent remembers the last record it sent for each log and event id. It starts at the newest record,
  so a new rule raises nothing for history, and it notices a cleared log and reads from its start, so the clearing itself is found.
- **Limits.** At most 50 events for an id and 300 lines in one report, and one check-in spends at most 40 seconds. A host reads at most 12 event ids
  of each log, its own rules and the fleet-wide ones together, and every place that saves rules refuses a thirteenth, because the agent would never
  read it.
- **A name in an event can have been typed by anyone,** the user of a failed logon for one. Every text is cut at 64 characters, characters that hide
  or reorder text become spaces, and a password in the program a new service or task runs is replaced.

See [Windows event rules](log-watch.md#windows-event-rules).

### What starts by itself

A person who has got into a Windows host usually leaves something that starts again by itself. The agent lists five places, at most every 15 minutes,
by path and name only: the `Run` and `RunOnce` keys of `HKLM` in both views, the Winlogon `Shell` and `Userinit` values, services that run from a
temporary or user folder, scheduled tasks that are not Microsoft's, and the startup folders of all users and of each profile. It checks no signature,
opens no program and writes nothing. The **Persistence** section of the host's drawer shows what was added and removed, and what is on the host now.

- **The first inventory is the baseline** and raises nothing, so a new host or an updated agent is quiet.
- **A new entry raises one alert** for the host, `persistence_added`, at most one an hour. It is in the Alerts inbox and Recent Activity, does not
  page, and its webhook is off until you turn it on for the kind **New startup entries on Windows hosts**. A removed entry is logged and never alerts.
- **A place that is cut or unread is still compared.** If the agent could not read a place whole, an entry it shows that the last whole read does not
  hold is new and alerts once, and nothing is read as removed. A place that is not whole three inventories in a row raises one `persistence_unread`
  alert. A terminal server with many profiles stays cut, so mute that event for it.
- **A password in a command line is replaced** before the list leaves the host and again on the server.

Not listed: the `Run` keys of a user, WMI event subscriptions, Image File Execution Options, AppInit_DLLs, and the autostarts of macOS and Linux
hosts. There is no way yet to accept the current state or clear the log. See [Persistence inventory](windows-client.md#persistence-inventory).

## Linux hosts

These need the Linux agent from 8.0.2.

### Check for updates now

**Scan now** reads what the package manager already has. On an apt host that is the lists as they were last downloaded, so a host whose lists are a
week old reports a week-old answer. Open a Linux host, open **Packages** under **Software** on its **Audit** tab, and press **Check for updates now**.
The agent runs its distribution's own fixed command (`apt-get update`, `dnf makecache --refresh`, `yum makecache`, `zypper --non-interactive refresh`
or `apk update`), gives it no input, waits at most 30 seconds for another package manager's lock and ends it after 120 seconds. When the lists were
refreshed, fully or partly, it reads what is pending against them. **Lists refreshed** and **how it went** show on the Packages section: one of four
statuses and one of ten reasons from a fixed list, never the package manager's own output.

- **On Arch the refresh uses `checkupdates`** from `pacman-contrib`, which syncs a private copy of the databases and cannot cause a partial upgrade.
  Without it the answer is "not refreshed: no safe way on this distribution": nothing is run and no scan follows. The scan that reads what is pending
  is a different command and has not changed: on Arch it syncs the host's databases with `pacman -Sy`, as it always did, so the install hint for a
  missing tool there is `pacman -Syu <package>`.
- **Who and when.** Anyone who may patch the host can ask. It is a queued command, so maintenance mode, a quarantined host, an agent in audit mode and
  a change window that holds commands apply, and it can wait for a second admin if you put the **Scan** kind under change approval. It is not offered
  for Windows and macOS hosts, for hosts without an agent, or from the containerized agent. An agent older than 8.0.2 does not know the command, so
  the request is refused with a 409 and a sentence and nothing is queued.
- **Before each scheduled scan.** **Settings → Security → Package lists** has **Refresh the package lists before each scheduled scan**. It is off by
  default, and with it off a scan does what it always did.
- **The check** *Package index updated recently* reads the stamp the agent writes on success, so it works on dnf, zypper and apk hosts too. A check
  you applied from the template earlier keeps its two apt paths until you edit it or apply the template again.

See [Refreshing the package lists](patches.md#refreshing-the-package-lists).

### What this agent can see

A feature without its tool used to show up as one missing signal or an empty page. The **Audit** tab of a Linux host's drawer has a new section under
System, **What this agent can see**. It says whether the agent runs as root or in a container, which of the 25 tools it uses are on the host, the
distribution and the init system, the logs the threat sensor found and whether the agent can open each (the path and a yes or no, never a line of a
log), and the agent's version and Python. A missing tool is listed with the feature that needs it and a fix: the install command for the host's
package manager, or a short sentence where no command is right for every host. A tool that a feature does not need on this host (another
distribution's package manager, `systemctl` on a host without systemd) is not listed as missing, and in a container a tool that is not in the image
says **not available in a container**. A tool you install shows at the agent's next report, about ten minutes. See
[the troubleshooting guide](troubleshooting.md).

## Vulnerabilities

### Which packages were checked

A scan used to say what it found, and "none found" read as "clean" for packages that were never asked about under the name the advisory data is filed
under. Now every package a host listed is checked, or has one reason it was not: no source name, no matcher for the package manager, release not
known, past the limit of 10,000 packages a scan reads, or not answered in full by the data source. The imported GPG keys of an RPM host are not
software and are not counted.

- The CVE page has a line under the tiles with the fleet total, the reasons and the five hosts with the most packages not checked. A click on a host
  opens its view.
- The host view says **Packages checked**. A click shows the reasons with their counts and the first 200 packages that were not checked. A host with
  no finding says **None found in the packages that could be checked**, and "No vulnerabilities found" only when every package was checked.
- The host drawer's badge reads *none found* and not *clean*, and the Home tile is neutral and not green when part of the fleet was not checked. The
  assistant's CVE tool, the text of a ticket, the runbook, the MCP tool `get_cves` and the SBOM say the same.
- **A host states its packages from its next scan.** Run **Scan all hosts** once. Until then the line under the tiles says how many scanned hosts it
  does not count yet. A host that nothing is matched against, such as an Arch or Windows host, says so at once.

The data source answers the same for a package it has no record of as for one that no advisory touches, so a package from a third-party repository
counts as checked on a host that is asked by source package. See [Which packages were checked](cve.md#which-packages-were-checked).

### The kernel a host runs

A scan used to match the findings of the kernel against every kernel version a host has installed, so a replaced kernel's findings were counted beside
the one that runs, and a fix that sat in a kernel the host had not booted into was offered as an update to install. The Linux agent now reports the
kernel it runs and, for each installed kernel image, the release it owns. It reads the package database and the host's files and never guesses from a
name.

- When exactly one installed package owns the running release, the scan asks about and counts that package only. The kernels that do not run are left
  out, and the host view says how many packages that is.
- A finding of the running kernel that a newer installed kernel already fixes reads **Fixed by an installed kernel, reboot to apply**. It names that
  kernel and offers nothing to install, and the CVE page has a sixth tile for it, **Reboot to apply**. Installing the update does not announce it as
  cleared: it clears, once, at the scan after the reboot.
- It counts and it alerts, because a reboot is something to do. The two options that count and alert only on what can be fixed now say **an update or
  a reboot**.
- When the scan cannot tell which package the host runs, it matches every installed kernel as before, and the host view says so and why. An agent
  older than 8.0.2 reports no kernel, and neither do the Windows and macOS agents.

A kernel livepatch was not looked at: a host that has the fix live would read "reboot to apply". See
[The kernel a host runs](cve.md#the-kernel-a-host-runs).

## Smaller changes

- **Date order and clock.** **My Account → Profile → Language** has **Date order** (Automatic, day first, month first or year first) and **Clock**
  (Automatic, 24-hour or 12-hour). They are saved to your account, so they follow you to other browsers, and **Automatic** writes what the page wrote
  before. Day first reads 7/11/2026 in English and 7.11.2026 in German, and year first is always 2026-11-07. E-mails, exports, the public status page,
  the customer portal, the printable report and the fleet query page keep their own formats. See [My Account](my-account.md).
- **Preview members.** The smart-group editor has a button that shows how many hosts the rules match, and the first 50, before you save. The count comes
  from the same check the saved group uses. You see only your own tenant's hosts, and a key with a host scope only the hosts of its scope. A preview
  stores nothing. See [Groups](sites.md#the-groups-tab).
- **A failing destination is marked.** After three failed deliveries in a row the card of a destination in **Settings → Notifications** shows a red
  **Failing** mark, how many deliveries failed in a row and the kind of the last error, never the address. Only the administrator sees it. It goes when a
  delivery gets through, and when you change the destination's address, format or credentials. See
  [A destination that keeps failing](webhooks.md#a-destination-that-keeps-failing).
- **Keyboard focus rings are no longer cut off** in four scrolling lists: the AI Insights cards, a Knowledge base article, the Links page and a CMDB
  asset's documents. Focus also returns to a button whose handler disabled it, so a screen reader keeps its place.
- **A refused export is not saved as a file.** A tenant administrator who pressed **Export** used to be saved a `backup.zip` that held the error, under
  a green message. Nothing is saved now, the page says **Export failed**, and the **Backup & restore** card is drawn for the platform operator only.
- The time of a request sample on the Threat Intel page is exact when you hover it.

## Fixed on the way

- **A settings document applied back put `(redacted)` over the credentials of your destinations.** With a config master key set, applying an export
  unchanged replaced each destination's secret with that text, because destinations had no id to be matched by. They are matched by id now, and the
  preview of an import lists a destination as changed only when a field differs.
- **A failed read of the host store no longer empties what the sweeps keep for each host.** The health history, the metric and thermal roll-ups, the
  dependency edges and the Patch SLA aging took an unreadable host store for an installation with no hosts and dropped what they held. They keep it now
  and try again at the next pass.
- **Two stores that hosts write are written under their lock.** The software policy's violations and the brute-force detector's window lost entries when
  hosts sent together, which made `software_policy_violation` fire again for a host that had not changed, and made a brute-force alert late or lost.
- **Deleting a host clears the addresses its sensor queued** for Threat Intel.

## Found in review and fixed before release

The Windows items, the Windows security features, the Linux agent items and the CVE scan items were each read by a reviewer who had not written them,
and more than forty problems were fixed before this release. The four below are in features that are new in 8.0.2, so none is a flaw of an earlier release.

- **A standard user could silence the startup-folder and scheduled-task alerts for the whole host.** Fifty-one files in their own Startup folder made
  the agent send the whole startup place as not read, so the all-users folder and every other profile stopped being compared. And 201 tasks of their
  own made the task list cut, and a cut list was neither compared nor kept: the next whole read, with the decoys deleted and the payload still there,
  became the new baseline and nothing was reported. A cut or unread place is compared for what it shows now, and `persistence_unread` says when one
  stays that way.
- **A registry check printed a password** that sat inside the text of a value, such as a `Run` value, a service's `ImagePath` or a connection string,
  because its filter looked at the value name only. The program a new service or scheduled task runs had the same gap in the event lines. The password
  is replaced now, before the text is cut.
- **A host's malformed log entry broke the answer to its own heartbeat.** A log whose kind arrived as a list or a dictionary made the server answer
  500 on every beat that carried system information, and the host's packages, ports and posture stayed frozen while it kept beating and looked online.
  A wrong part of the report is left out now and the rest is kept.
- **A package list refresh that had waited a few seconds for a lock was ended as failed.** `dnf` prints its waiting line once, the watchdog searched
  everything the manager had printed, and a refresh that then downloaded normally was ended at the 30 second lock wait and recorded as "the package
  manager was busy". The manager is judged on its latest message now.

One older flaw turned up in the same review. A host or an entity row that a SQL backend (SQLite or PostgreSQL) read on its own skipped the repair that
a whole-store read applies, so a host whose stored packages were text made its Checks page answer 500 there and 200 on JSON. Both reads apply the
repair now. It needs a store that holds a value of the wrong kind, such as a hand edit or a restore.

## What was not tested

- **Nothing ran on a real Windows or macOS host.** The registry, the event log, PowerShell, `schtasks` and the Task Scheduler XML were exercised
  through stand-ins and sample output in the real formats, and the PowerShell scripts were parse-checked with `pwsh`. The software lists were tested
  with a stand-in for the registry, application bundles written to a temporary folder and a script in place of Homebrew. Whether every application
  that ships with macOS, Safari included, is listed is not confirmed.
- **No distribution's package manager was run for the refresh.** The commands were run against stand-ins that answer in each manager's own words,
  written from memory. The package names in the install hints of the capabilities section were not checked against real repositories, and a real
  container was not started.
- **The kernel mapping was checked against recorded data and constructed hosts only.** No Debian, Ubuntu, Rocky or Alpine host ran, and the kernel
  advisories in the tests were written for them.
- **The stores of the second half ran on JSON and SQLite, not on Postgres.** A Postgres test for the one-step update of a row was written and has not
  run.
- The date and clock choices were run in Chromium and in Node's engine. Firefox and Safari take month names and 12-hour spacing from their own
  engines.
- The recording behind Mean time to patch was tested by calling the sweep at chosen times, not over a week of real sweeps.
- There is no nginx on the machine this was built on, so `access_log off` was checked as text and against a model of nginx's rules, not on a running
  server.
